# 24 · 屏方向拍板材料（2026-10-02，只备料不动代码）

> `app_ui.c` 是 **320×480 竖屏**布局，`app_lvgl.c` 却把逻辑屏设成 **480×320 横屏**
> （`lv_display_set_rotation(90)`）⇒ 业务 UI 一旦启用就会被裁。
> 本文把证据、选项、判据收拢，**等你拍板**；拍板前一行代码都不动。

---

## 1. 现状证据

| 事实 | 出处 |
|---|---|
| 业务 UI 按 **320×480 竖屏**画（`UI_SCR_W 320` / `UI_SCR_H 480`） | `Task/Src/app_ui.c` 开头 |
| 逻辑屏被设成 **480×320 横屏**（rotation 90） | `Task/Src/app_lvgl.c` 的 `lv_display_set_rotation` |
| 模拟器实拍：业务 UI 内容只占左侧 320 列，右侧空底 + 冒出**滚动条**（480 高的界面塞进 320 高的屏） | `lv_port_pc_vscode-master/shots/g2026/02_ui_wave.png` |
| 板上当前跑的是 **demo**（`APP_LVGL_USE_DEMO=1`），业务 UI 不参与编译/运行 | `project_config.h` |
| 面板**认** MADCTL 的 90°（J-Link 直写实验：按横屏几何写四色条，屏上呈竖条） | 2026-10-02 排查记录（memory） |

⇒ **现状不炸**（demo 是横屏口径、与 rotation 90 自洽）；
炸的是"业务 UI 启用那一刻"—— 所以这是**重构开工前必须拍的板**。

## 2. A/B 对照表

| | **A：UI 重排成横屏 480×320** | **B：屏回竖屏 320×480** |
|---|---|---|
| 改动量 | `app_ui.c` 版式重做（工作量大，但正好就是"视觉重构"本体） | **1 行**：`set_rotation(90)` → `set_rotation(0)` |
| 业务 UI 何时可上板 | 重排完成后 | 改 1 行即可 |
| 与重构的关系 | 版式 + 配色/字号/质感一次做完 | 只做配色/字号/质感 |
| 风险 | 版式引入新 bug；工作量前置 | 低；demo 需按竖屏重看一遍 |
| 装配含义 | 产品横着装 | 产品竖着装 |

## 3. 拍照指引（5 分钟，定方向用）

1. 拍**当前运行中**的屏一张（demo 画面）。
2. 判读两点：
   - 屏上 demo 内容**有没有被裁/有没有滚动条** —— 没有 ⇒ demo 的横屏口径与面板自洽（预期如此）；
   - **你希望产品横着装还是竖着装** —— 这才是 A/B 的真正判据（屏的物理安装方向决定一切）。

## 4. 拍板后的落地步骤预览

- **选 A**：另立一份"业务 UI 横屏重排"计划（版式 → 模拟器验证 → 上板对照）；
  `app_lvgl.c` 不动。
- **选 B**：`app_lvgl.c` 的 `set_rotation` 改 0 → 模拟器重建出图（业务 UI 应完整显示）→ 真板对照；
  demo 侧同步看一遍（demo 是自适应画法，影响小）。

## 5. 我的建议（供参考，不算数）

**B 先行**：1 行、低风险、立刻让业务 UI 可上板；把"横屏版式"留给"视觉重构"阶段作为正式
版式再上（那时 A 的重排工作量才花得值）。
