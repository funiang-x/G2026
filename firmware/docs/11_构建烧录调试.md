## 1. 编译 + 构建

**唯一入口**：

```bash
python Tools/fw.py build                     # Debug 预设，增量
python Tools/fw.py build --clean-first       # ★ 判"零告警"只能用它
python Tools/fw.py build --preset Release    # 换预设
```

`--preset` 写在子命令前或后都可以（`fw.py --preset Release build` ≡ `fw.py build --preset Release`）。

**预设**（`CMakePresets.json`）：

| 预设 | 优化 | 用途 |
|---|---|---|
| `Debug` | `-Og -g3` | 日常开发、单步调试 |
| `Release` | `-Os -g0` | 发布；**体积最小** |
| `RelWithDebInfo` | `-O2 -g3` | 现场取证 / profiling |
| `Debug-UART` | `-Og -g3` + 日志走 USART1 | 手边没有 J-Link 时用（见 §3） |

⚠️ **Release 用 `-Os`，不要改回 `-O3`**：实测 `-O3` 会让 SEGGER RTT / HAL 这类按
`-O2/-Os` 写的第三方代码激进内联，同一份代码反而**多 7.3 KB**（全在第三方符号上）。

### 零告警口径（硬门禁）

```bash
python Tools/fw.py build --clean-first
```

**判据**：`warning` + `error` 总数为 0，且**没有新增 `-Wno-*`**。

⚠️ **"零告警"只在 `--clean-first` 之后才有资格说**：增量构建只重编改动过的文件，
只在别处触发的告警会被漏报 —— 实测过：一次注释改动让 3 个预设报 `-Wcomment`，
另 2 个因未重编而"看起来干净"。（顺带记住这个坑：注释体内出现 `/*`，
例如写路径 `Core/Src/*.c`，就会触发 `-Wcomment`。）

### 工程代码的告警档位

| 目标 | 告警 |
|---|---|
| `common` / `operation` / `device` / `task` | **全套**（`proj_warnings`：`-Wall -Wextra -Wshadow -Wundef -Wstrict-prototypes -Wdouble-promotion -Wmissing-prototypes -Wpointer-arith -Wcast-align`） |
| 可执行目标自己的源码（`Core/Src` 全部 = 生成物）、`SEGGER_RTT`、ST HAL、FreeRTOS | 只 `-Wall` |

**生成物为什么只给 `-Wall`**：ST 的代码风格在 `-Wextra` 下必然有告警，而 CubeMX
每次重新生成会反复报同样的 —— 压不住的告警等于没有告警。实测：`syscalls.c` 与
`sysmem.c` 在严格档下报 **19 条**（newlib 桩函数天生没有原型），且每次生成都原样回来。

⚠️ **`proj_warnings` 必须用 `PRIVATE` 挂在四个层上** —— 写成 `PUBLIC` 会顺着
`device`/`task` 传到可执行目标，把严格告警灌到生成物上（实测：那 19 条就是这么来的）。

⚠️ `Core/` 里只有 `main.c` / `freertos.c` 的 `USER CODE` 段是人写的，它们只拿
`-Wall` —— **刻意如此**：那里只该写胶水（一个 `#include` + 一次调用），
写了几十行逻辑就已经越层了。

## 2. 烧录（J-Link SWD）

```bash
python Tools/fw.py flash                     # 烧 Debug
python Tools/fw.py flash --preset Release
python Tools/fw.py flash --erase             # 先全片擦除再烧（⚠️ 见 docs/12，AI 不碰）
```

底层是 `JLink.exe -CommanderScript`，脚本按 `build/<preset>/board.env` 的
`JLINK_DEVICE` 生成。那份 `board.env` 是 CMake 的生成物，器件名与内存容量来自
`Core/Inc/board_config.h` ⇒ **换板子只改 `board_config.h`**，脚本与体积门禁跟着变。

⚠️ **烧录是不可逆操作**（会覆盖目标 Flash 上现有固件）。`docs/12` 把它归到
「必须先说再做」档 —— AI 动手前要说明"烧哪个预设、连的是哪个探针"。
脚本用 `loadbin` + `verifybin`（**不用 `loadfile`**：后者内容一致就**跳过下载**，
探针不稳时这个比较会误判 ⇒ 根本没烧却不报错，实测中过一次）。

### 探针连不上时的排查顺序

**★ 先分清「探针层」还是「目标层」**：报 `Cannot connect to the probe/programmer`
⇒ **探针**自己的 USB 没通（与目标板无关）；报 `Failed to initialize DAP`
⇒ 探针通了，但 **SWD 两根线**连不到芯片。

1. **`Get-PnpDevice -PresentOnly | ? InstanceId -match VID_1366`** 是**权威判据**。
   ⚠️ `fw.py env` 读的是 `ShowEmuList`，**可能是缓存** —— 实测遇到过
   "`env` 说在线、PnP 说没有、实连卡死"三者不一致。
2. 探针层：换 USB 口（直插机箱后面板）/ 换数据线 / 拔插。克隆探针常见（`S/N: -1`）。
3. 目标层：`VTref` 读到 3.3V ⇒ 3V3/GND 已通，问题只剩 SWDIO/SWCLK（**最易接反**）。
   本板调试口是 **H1**，引脚定义见 `guides/01`。`--erase` **不是第一选择**。
4. ⚠️ **`flash` 报 `Contents already match / Skipped` 不要当成功**：探针不稳时
   它的"读回比较"会**误判**，于是**根本没烧**却不报错（实测踩过）。

## 3. 日志（SEGGER RTT）

```bash
python Tools/fw.py rtt                       # 前台抓，Ctrl+C 停
python Tools/fw.py rtt --duration 5          # 抓 5 秒
```

底层 `JLinkRTTLogger.exe`，**通道 0**。源码在 `Middlewares/RTT/`，无需外部依赖。
**为什么用 RTT 而不是串口**：不占串口、不打断实时性（RTT 是内存环形缓冲，目标侧
只做 memcpy）、不需要额外接线 —— 调试探针插着就能看日志。

### ⚠️ RTT 丢数据（最容易误判的一类"故障"）

**上行缓冲默认只有 1024 B**，模式 `NO_BLOCK_SKIP` —— **满则直接丢**，不阻塞不报错。
`verify` 是"先复位放行、再挂 RTT 主机"⇒ **开机瞬间的批量输出会整段丢掉**（实测
153 个值只收到 18 个，日志在 1024 B 处直接跳到结束标记，看着像"算错了"）。
两条对策缺一不可：① 批量输出**分块让路**；② **等主机挂上再发**
（见 `project_config.h` 的 `APP_TRACE_START_MS`）。

⚠️ 丢数据是**静默**的 —— 消费端必须做完整性断言（收到的条数与期望比对）。

### 日志接口

```c
#include "log.h"
LOG_I("uart ready, baud=%u", baud);
```

⚠️ 不要直接 `printf`，也不要直接调 `SEGGER_RTT_Write`（通道规划在 `Device/Inc/rtt_channels.h`）。
⚠️ **不要用 `%f`** —— 见 `09` §7。

### UART 后端（`--preset Debug-UART`）的三条硬约束

**① MSP 归 CubeMX。** `HAL_UART_MspInit` 生成在 `Core/Src/usart.c`（引脚/复用/时钟
都在里面）；`bsp_log.c` 再定义一份 ⇒ 链接期 `multiple definition`。
⚠️ 参考工程 `template` 自己写 MSP 且**能编** —— 因为那边没配任何 USART。
**本工程配了 USART1，那条路走不通**，别照抄；也别删 `usart.c` 的 MSP（生成物）。

**② `.ioc` 里必须至少配一个 USART**，否则没有 MSP ⇒ "编得过但串口一声不响"。
`bsp_log.c` 用 `HAL_UART_MODULE_ENABLED` 把它变成**编译期错误**。

**③ `board_config.h` 里那五个 UART 引脚宏（`BOARD_LOG_UART_TX_PORT` 等）是"登记项"**：
改它们**不会**改引脚（要去 CubeMX 改），只供 `fw.py lint` 对账。真正被
`bsp_log.c` 读的只有 `BOARD_LOG_UART_PORT` 与 `BOARD_LOG_UART_BAUD`。

## 4. 调试（GDB）

```bash
python Tools/fw.py gdb                       # 启动 GDB server + gdb（交互）
python Tools/fw.py gdb --server-only         # 只起 server，自己接别的前端
```

底层：`JLinkGDBServerCL.exe -device STM32F407VG -if SWD -speed 4000 -port 2331`
+ `arm-none-eabi-gdb build/Debug/<name>.elf`。

VS Code 里用 `launch.json` 的 Cortex-Debug 配置，等价于上面这条命令（见 `.vscode/launch.json`）。

### 崩溃现场怎么取证

`Device/Src/bsp_fault.c` 在 `HardFault_Handler` 里打印 PC / LR / CFSR / HFSR，
并**直接给出 `addr2line` 命令**。优先把那条命令跑一遍再下结论，不要靠猜：

```bash
arm-none-eabi-addr2line -pfiaC -e build/Debug/<name>.elf 0x0800xxxx
```

⚠️ `addr2line` **只对同一份 elf 有效** —— 重新 build 过就要换新 elf。

| 现象 | 先查什么 |
|---|---|
| HardFault | `bsp_fault_report()` 的输出 → PC 落在哪个函数 |
| 卡在 `Error_Handler()` | 某个 `MX_*_Init()` 返回非 `HAL_OK`；时钟配置最可疑 |
| 任务完全不跑 | `osKernelStart()` 是否被调用；`configTOTAL_HEAP_SIZE` 是否够 |
| `malloc` 返回 NULL | 堆耗尽 → `sizecheck` 看 RAM 账目 |
| 日志突然中断 | 先排除 RTT 丢数据（见上），再看是不是死锁 |

## 5. 闭环验证（`verify`）

```bash
python Tools/fw.py verify --duration 8
```

做五步：**配置对账 → 编译 → 体积门禁 → 烧录 → 抓 RTT 判标记**。

前两步门禁（`lint`、`sizecheck`）排在烧录**之前**，理由是它们秒级且不碰硬件 ——
配置层面就矛盾、或体积已超预算时，烧录是白费；而烧录是**不可逆操作**
（docs/12 §B），不该拿它当"顺便检查一下"。任一门禁不过就中止，不浪费一次烧录。

⚠️ `verify` 要求 RTT 日志后端。用 `--preset Debug-UART` 跑它会**直接拒绝**
（退出码 6）—— 串口后端没有"标记落在哪"的约定，判不出来就是判不出来，
不假装能判。

| 退出码 | 含义 |
|---|---|
| **0** | 看到 `BOARD_BOOT_OK_MARKER`（`[AI_READY]`）⇒ 固件真的跑起来了 |
| **1** | 看到 `BOARD_BOOT_FAIL_MARKER`（`[AI_FAIL]`）⇒ 固件主动报错 |
| **2** | 超时，两个标记都没看到 ⇒ **探针/接线/固件卡死，原因未知** |

⚠️ **退出码 2 不等于"固件有问题"** —— 也可能是探针没插、串口被别的工具占着。
先 `fw.py env` 确认探针在线。

⚠️ **探针不在线时，不要把"编译通过"说成"验证通过"** —— 见 `AGENTS.md` §交付口径。

## 6. 体积

```bash
python Tools/fw.py size                      # 看明细
python Tools/fw.py sizecheck                 # 门禁：超线即失败
```

**只认一个口径**：`Tools/stm32_size.py` —— 按链接脚本 `MEMORY` 区 + ELF 的 LOAD 段
边界计算，与 `ld` 打印的 `Memory region Used Size` **逐字节一致**。

⚠️ `arm-none-eabi-size` 的 Berkeley 三列**不等于**真实占用（section 间有 ALIGN 间隙，
且 `.data` 初值运行时在 RAM、烧写时在 Flash）。回答体积问题前先跑 `fw.py size`。

预算上限在该文件顶部的 `BUDGETS`（单文件实现，不另开 json），超线即判失败。
⚠️ **为了让 `sizecheck` 变绿而调高上限 = 把门禁拆了。** 要调先说清理由（见 `docs/12`）。

## 7. 电脑上跑单测（不需要板子）

```bash
python Tools/fw.py test
```

用 **host gcc** 编译 `Operation/` 的源码 + `Test/` 的用例并运行。
这是本工程**最重要的反馈回路**：秒级、不烧板、不需要探针。

它同时是**规矩 2 的第二道墙** —— 谁在 `Operation/` 里偷用硬件函数，
这里会报 `undefined reference to vTaskDelay`（见 `01` §强制表）。
这条不是设计意图，是**实测过**的：`fw.py selftest --full` 会注入这个违规并断言它失败。

⚠️ **"跳过"不等于"通过"**：一个用例都没注册时 `ctest` 会跑出 0 个测试并**退出码 0**
—— 那意味着规矩 2 的强制**未经验证**。`fw.py test` 把这种情况单独判成退出码 **9**
（与断言失败同一个码），并在输出里说清是"断言挂了"还是"一个用例都没有"。

## 8. 文档一致性（死链 + 陈旧标识符）

```bash
python Tools/fw.py doccheck
```

扫三类：反引号里的路径 · 围栏代码块里的命令 · **工程自有标识符**
（`op_`/`bsp_`/`app_`/`LOG_`/`APP_`/`BOARD_` 前缀的名字必须在代码里存在）。

⚠️ **两类问题都是无声的** —— 死链不报错，直到某次 AI 按错的路子干了活；
陈旧标识符更隐蔽：文档写在实现定型之前时函数名会变（实测一次抓出 6 处），
固件照编、门禁全绿，直到 AI 照文档写了一个不存在的函数名才炸。
⚠️ 只查名字是否存在（不查签名/参数个数）；`docs/02`~`09` 是示例型规范，
名字本来就是虚构的，不参与对账 —— 改那几篇时靠人核。

## 9. 门禁自检

```bash
python Tools/fw.py selftest                  # 静态门禁
python Tools/fw.py selftest --full           # 追加编译期用例
```

在**工程副本**上跑三组（原工程全程只读）：**基线**（无注入时全绿，排除"永远报错"
的假检查器）→ **负向用例**（注入真违规，必须报错，排除"什么都不做"的假检查器）
→ **正向用例**（注入合法写法，必须仍通过，排除"什么都报"的假阳性）。

⚠️ **"退出码 0"不是有效判据** —— 一个什么都不做的检查器同样返回 0。
静态检查器的失效是**无声的**：不报错、不影响构建、报告照样全绿。
