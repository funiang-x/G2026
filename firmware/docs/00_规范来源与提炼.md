## 一、从 template 提取（工程侧）

### 1.1 目录结构 —— 采纳

```
Task/       调度：什么时候做（FreeRTOS API 只在这层）
  ↓
Operation/  业务：吃数字吐数字（不碰硬件、不用 RTOS）⇒ 能在电脑上编译+单测
  ↓
Device/     设备：怎么操作一个硬件（唯一能用 HAL 的层）
  ↓
Core/ + Drivers/   CubeMX 生成 + HAL / CMSIS

Common/     横切：日志 / 错误码（谁都能用，但它自己零依赖）
project_config.h   应用参数（周期 / 阈值 / 开关），不含任何 HAL 内容
```

**采纳，一字未改。** 理由是它回答了一个具体问题：**业务逻辑怎么在电脑上验证**。
分成"调度 / 业务 / 设备 / 生成"四段，是为了让 `Operation/` 里只剩纯计算 ——
纯计算才可能脱离板子跑单测。分层不是为了好看。

### 1.2 四条规矩 —— 采纳

| # | 规矩 | 处理 |
|---|---|---|
| 规矩 1 | 只能上层调下层，不能跳层 | **原样采纳** |
| 规矩 2 | `Operation/` 不碰硬件、不用 FreeRTOS | **原样采纳**（含 `now_ms` 参数化的写法） |
| 规矩 3 | 中断代码归 `Device/`，投事件通知上层 | **原样采纳** |
| 规矩 4 | CubeMX 代码只在 `USER CODE BEGIN/END` 间写 | **采纳 + 扩写**（见 1.3） |

规矩 4 在本工程被**扩写**，因为本工程的 CubeMX 链路和 template 不同：

- template：CubeMX 生成到沙盒 `CubeMX/sandbox/gen/`，再由 `cmx_gen.py` + `cmx_apply.py`
  搬进 `Core/`（两段式，中间要合并 USER CODE）；
- 本工程：**CubeMX 直接生成到工程根**，`Core/` 原地更新，USER CODE 由 CubeMX 自己保留
  （依据：实测 `CMakeLists.txt` / `CMakePresets.json` 不会被覆盖，见
  `../../template/.workbuddy-ai/memory/2026-09-21.md`）。

⇒ 所以规矩 4 在本工程是**三条禁令**：① 非 USER CODE 区不写；② 不手改 `Drivers/`；
③ 不手改 `cmake/stm32cubemx/CMakeLists.txt`（生成物）。细则见 `docs/01` §规矩 4。

### 1.3 分层靠什么强制 —— 采纳（这是整套规矩里最值钱的部分）

template 的做法：**不写检查器，用 CMake 的链接与 include 可见性固化**。

| 规矩 | 强制手段 | 失效时 |
|---|---|---|
| 2（不碰硬件） | `operation` 目标只链 `common` ⇒ 拿不到 HAL 头 | 编译期 `fatal error: stm32f4xx_hal.h: No such file` |
| 2（防绕过） | PC 侧构建里没有 HAL / FreeRTOS 符号 | 链接期 `undefined reference to vTaskDelay` |
| 1（不跳层） | CMake 管不了（只有目标级粒度） | 靠约定 + review |
| 4（USER CODE） | 靠理解 CubeMX 行为 | **覆盖后没有报错**，只是代码没了 |

**采纳。** 这条比"写个 lint 脚本"强的地方在于：**编译器不会忘记运行**。
本工程不移植 template 的 `check_layering.py` 等检查器，正是因为不需要它们。

### 1.4 其他工程资产 —— 逐条取舍

| 资产 | 处理 | 理由 |
|---|---|---|
| 严格告警 `proj_warnings`（9 个 `-W*`） | **采纳** | 零告警是本工程的硬门禁，见 `docs/11` |
| "零告警只在 `--clean-first` 后算数" | **采纳** | 增量构建漏报过真实告警（2026-09-13 实测） |
| 生成物只给 `-Wall`、不套严格告警 | **采纳** | CubeMX 重新生成会反复报同样的告警，压不住等于没有 |
| `core_generated` 必须是 OBJECT 库 | **采纳** | STATIC 会在链接顺序上踩 `undefined reference to __errno` |
| 体积预算门禁 `sizecheck` | **采纳**（精简为单文件实现） | 见 `Tools/stm32_size.py` |
| `fw.py` 统一命令入口 | **采纳**（子命令精简） | 见 `docs/11` |
| PC 侧单测 `Test/` | **采纳** | 规矩 2 的兑现方式 |
| 门禁自检 `selftest.py`（负向用例） | **采纳** | "退出码 0 不是有效判据" |
| SEGGER RTT 日志 | **采纳**（vendor 到 `Middlewares/RTT/`） | 不占串口、不打断实时性 |
| J-Link SWD + Cortex-Debug | **采纳** | 本机 J-Link V936 |
| **CubeMX 沙盒 + `cmx_gen.py`/`cmx_apply.py` 搬运** | **放弃** | 见下 |
| **`fetch_deps.py` 钉版本拉取 HAL/CMSIS** | **放弃** | 见下 |
| **CMSIS-DSP** | **放弃**（本工程不带） | 见下 |
| **LVGL** | **放弃** | template 已移出，本工程同样不做 GUI |
| **CCM RAM 段 + `ccmram.c`** | **暂缓** | F407VG 有 64KB CCM，值得用；但属"用起来再加"的优化，见 `docs/12` 的提案位 |
| **`check_layering.py` / `check_doclinks.py` / `check_docs.py`** | **放弃** | 前两个由 CMake 强制取代；第三个由 `Tools/check_doc_links.py` 取代（见 2.2） |

#### 为什么放弃「CubeMX 沙盒 + 搬运」

template 用沙盒，是为了让 `Drivers/` 能钉版本（避免 CubeMX 的 CMSIS 5.6.0 覆盖模板钉的 5.9.0）。
本工程的取舍相反：**直接用 CubeMX 生成到工程根，库版本跟着 CubeMX 走**。

代价要认：换 CubeMX 固件包版本可能引入新告警，而本工程要求零告警 —— 这两条会互相打架。
处理方式：**固件包版本在 `.ioc` 里锁死**（`ProjectManager.FirmwarePackage`），
升级前必须先跑一次全预设复验。见 `docs/12` 的安全规则。

收益：少一个环节、USER CODE 自动保留、`Core/` 不再是"搬运目标"、心智模型更直白。

#### 为什么放弃 CMSIS-DSP

template 带 DSP 是因为它的产品目标是信号采集分析仪。本工程是**空白模板**，
不该预置任何一个具体产品的依赖 —— 需要时再加，加法写进 `docs/10`。

## 二、从 esp32_prj 提取（文档侧）

### 2.1 骨架 + 编号子文档 —— 采纳

| 机制 | 说明 | 采纳 |
|---|---|---|
| `AGENTS.md` 是**骨架**，≤ 100 行 | 只放"动手前必须知道"的硬事实 | ✅ 本工程预算放宽到 ≤ 110 行 |
| 细则一律进 `docs/0x_*.md` | 超过 3 行的展开都不留在骨架里 | ✅ |
| 骨架用**短引用** `docs/01` 而不是全名 | 为省骨架行数 | ✅ |
| `docs/README.md` 是索引 + 预算表 | 超预算说明该**合并**，不是该再拆 | ✅ |
| 三类文档分开：规则 / 教程 / 历史 | 历史不进骨架引用面 | ✅（`docs/guides/`、`docs/archive/`） |
| 文档状态标注：已定稿 / 从代码提取待确认 / 待确认 | AI 不得自行填充"待确认"文档 | ✅ |
| 提案流程 `docs/13` | AI 写提案（带证据）→ 人审核 → 才写入 | ✅ |
| 变更记录表在骨架 §8 | 谁改的、谁批的 | ✅ |

### 2.2 死链门禁 —— 采纳并**扩了一条**

esp32_prj 的 `tools/check_doc_links.py` 扫两类引用：反引号里的路径 + 围栏代码块里的命令。
本工程**原样采纳这个双扫描**，因为骨架用短引用 `docs/01`，肉眼看不出对错，必须靠工具。

> 这条来自 esp32_prj 的一次真实提案（`notes/2026-09-20_规范提案包.md` 提案 C′）：
> 只扫反引号时，"删了脚本但文档还教人跑它"这类死链**不会被发现**。

### 2.3 安全规则 —— 采纳并**大幅扩写**

esp32_prj 的 R5（必须先问人的清单）是本工程 `docs/12` 的原型。本工程扩写的原因：
**STM32 侧的不可逆操作比 ESP32 多得多** —— 擦片、烧错器件、改时钟树导致板子起不来、
`git stash` 在本机有丢提交的前科（template 实测丢过 36 个提交）。

⇒ 本工程把它从"一条 R5"升级成**独立的一篇 `docs/12`**，并区分**三档**：
可直接做 / 必须先说再做 / 必须人来做。细则见 `docs/12`。

### 2.4 不采纳的部分

| 机制 | 为什么不采纳 |
|---|---|
| `sdkconfig` / `managed_components` 只读那套 | ESP-IDF 专有，STM32 侧对应物是 `Drivers/` 与 `cmake/stm32cubemx/` |
| 组件式目录（`components/<层前缀>_<名>/`，每个组件一个 `CMakeLists.txt`） | ESP-IDF 的构建模型要求这么做；CMake 侧不需要，四层各一个 STATIC 目标更简单 |
| `idf.py monitor` 崩溃自动翻译 | 无对应物；STM32 侧用 RTT + GDB，见 `docs/11` |
| 12 号文档位 | 本工程 12 号已被安全边界占用 |

## 三、本工程与两个来源的差异（一句话版）

| 维度 | template | esp32_prj | **本工程** |
|---|---|---|---|
| 芯片 | STM32F405RG | ESP32-S3 | **STM32F407VGT6**（1MB Flash / 192KB SRAM / 64KB CCM） |
| CubeMX | 沙盒 + 两段搬运 | 无 | **直接生成到工程根** |
| 第三方依赖 | 钉版本拉取 | 组件管理器 | **跟着 CubeMX 固件包**（`.ioc` 锁版本） |
| 规则载体 | `AGENTS.md` 单文件 40KB | 骨架 100 行 + `docs/01~13` | **骨架 + `docs/00~13`**（本工程即两者的合并） |
| 门禁 | lint + 零告警 + 体积 + selftest | 零告警 + sizecheck + doccheck + selftest | **零告警 + 体积 + doccheck + selftest** |
| 预置外设 | 空白 | BSP + LVGL 演示 | **SPI2 / USART1 / USB_OTG_FS + FreeRTOS**（沿用现有 `.ioc`） |

**特点归纳（三条）**：

1. **规矩有强制点，不靠自觉** —— 四条规矩里三条有编译期或链接期的机器强制（`docs/01` §强制表）。
   剩下的那条（不跳层）明确标注"CMake 管不了，靠 review"，不假装它有兜底。
2. **文档有预算，超了要合并** —— 骨架 ≤110 行、单篇 ≤300 行、规范文档 ≤14 篇。
   理由是来源里的原话：「工具规则太复杂就会弃用」。
3. **AI 的操作范围是明写的** —— 不是"希望 AI 谨慎"，而是三档清单 + 可执行的判据（`docs/12`）。
