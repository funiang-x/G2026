# 12 — 安全边界（AI 的操作范围）

> 状态：**已定稿**（2026-09-21）
>
> **本篇优先级高于 `docs/01`~`11`。** 冲突时：**安全 > 分层 > 风格**。
>
> 这份文档存在的理由：AI 干活很快，而嵌入式工程里有一批操作**不可逆** ——
> 擦掉整片 Flash、把时钟树改错导致板子起不来、用 `git stash` 丢掉整个仓库的历史。
> "希望 AI 谨慎"不是工程手段，**可执行的清单**才是。

## 0. 工作范围（文件边界）

| 允许 | 禁止 |
|---|---|
| 本工程根目录下的文件 | **工程根之外的任何路径**（桌面、用户目录、其它工程） |
| 读 `Drivers/`（只读） | 改 `Drivers/` 下的任何字节 |
| 在 `build/` 下构建 | 用 `build/` 存放非构建产物 |
| 在 `.workbuddy-ai/memory/` 写记忆 | 删除 `.workbuddy-ai/` 目录本身 |

⚠️ **不确认路径就不动手。** 删/改之前先 `ls` 确认目标存在、且在本工程内。

## 1. 三档授权

### A 档 —— 可直接做（可逆，或只影响构建产物）

- 读任何文件、跑 `python Tools/fw.py env`
- `fw.py build` / `test` / `doccheck` / `selftest` / `size` / `sizecheck`
- 新增文件：`docs/` 新文档、`Test/` 新用例、`Operation/` 新模块、`Device/` 新驱动
- 改**自己刚写的**文件
- `fw.py clean`（**只删 `build/`**）

### B 档 —— 先说再做（说清"改什么 / 为什么 / 怎么回退"，等确认）

| 操作 | 为什么是 B 档 |
|---|---|
| 改 `Core/Inc/board_config.h` 的引脚 / 时钟 | 改错 ⇒ 板子起不来，且**编译不报错** |
| 改 `project_config.h` 的行为参数 | 会改变产品行为 |
| 改 `CMakeLists.txt` 的目标划分 / include 归属 | 动过一次就出过"只有部分预设能编过"（见 `01` §强制表） |
| 改 `.ioc` 并重新生成 | 会覆盖 `Core/` 下的生成物 |
| **烧录**（`fw.py flash`） | 覆盖目标 Flash 上现有固件 |
| 改 `Tools/` 下的门禁脚本 | 必须**同时**配负向用例（见 `11` §9） |
| 改 `docs/` 里标「从代码提取，待确认」的条款 | 那是在**替人拍板** |
| 加 / 删第三方依赖 | 影响体积与告警基线 |
| 新建 / 删除整个目录 | 影响面大 |

**B 档的交付格式**（缺一不可）：

```
要改：<具体文件 + 具体行/符号>
为什么：<触发原因>
影响面：<哪些东西会跟着变>
回退：<怎么退回去>
```

### C 档 —— 必须人来做（AI 不碰，也不"变通绕过"）

| 操作 | 理由 |
|---|---|
| `git stash` / `git stash push` | **本机 git 有实测前科**：2026-09-13 一次 stash 在 repack 中途中止，旧 pack 已删、新 pack 未写出，**36 个提交的对象全部丢失、不可恢复** |
| `git reset --hard` | 本机 git 只更新 HEAD 与索引，**不写回工作区**（`git status` 报大量 ` D`，而 `git ls-tree` 证明树里还在） |
| `fw.py flash --erase`（全片擦除） | 会抹掉目标上的一切，包括选项字节以外的现场 |
| 改 `.ioc` 的固件包版本 / 升级 CubeMX | 库版本跟着变 ⇒ 可能引入新告警，与"零告警"门禁打架 |
| 改 `Tools/stm32_size.py` 的 `BUDGETS` 上限 | **为了让 `sizecheck` 变绿而调高上限 = 把门禁拆了** |
| 改 `AGENTS.md` | 骨架**只有人能改**（见 `docs/13`） |
| 改 `docs/` 里标「已定稿」的规范条款 | 同上；要走 `docs/13` 的提案流程 |
| 删除任何**不是本次生成**的文件 | 删除前必须能回答"这个文件是谁建的、删了谁会坏" |
| 动 `Drivers/` 下的内容 | 生成物，重新生成即还原 |

**回退一律用**：`git revert` 或 `git checkout <rev> -- <path>`。
要暂存改动就**手工复制文件**，不要用 stash。

> 这条禁令已经写进本机 git 配置（`gc.auto=0`、`maintenance.auto=false`），**勿改回**。

## 2. 绝对禁止（任何档位下都不做）

| 禁止 | 说明 |
|---|---|
| `rm -rf` / `del /S /Q` / `shutil.rmtree()` 打在**工程外**路径 | 见 §0 文件边界 |
| 对 `Drivers/`、`Core/`、`Middlewares/` 做递归删除 | 都是生成物或 vendor，重建成本高 |
| 改 `.git/config` 或 `gc.auto` | 那两条是为防事故故意设的 |
| 调用 Windows LOLBin（`schtasks.exe` / `cscript.exe` 等） | 本机安全黑名单拦截，且明确要求**不要重试或变通** |
| 为了让编译过而 `-Wno-*` / 关告警 | 见 `08`；除非说清"为什么这条告警在本文件里无意义" |
| 伪造"已验证" | 没跑过的命令不要写"已验证"；硬件没上板就说"仅编译验证" |
| 编造寄存器位定义 / 复用号 / 引脚映射 | 查 `stm32f407xx.h` 与数据手册；拿不准就说"未验证" |
| 引用源码行号 | 见 `05` |

## 3. 动手前的四条纪律

### 3.1 先留退路

**任何 B 档以上改动，先做备份**：

```bash
cp -r <工程根> ../_backup_<日期>_<改造名>/
```

备份完**报出路径与文件数**，让"退路存在"这件事可验证，而不是一句承诺。

### 3.2 小步 + 每步可验证

一次只改一类东西，改完立刻跑对应门禁（见 `10` §交付前总检查）。
⚠️ **不要连续做多个不可逆动作再一起验证** —— 出错时无法定位是哪一步。

### 3.3 报告三态

| 标注 | 含义 |
|---|---|
| **已验证** | 写出跑了哪条命令、结果如何 |
| **未验证** | 说明为什么没跑（探针不在线 / 需要上板 / 需要人确认） |
| **不适用** | 说明为什么不适用 |

"编译通过" ≠ "能跑"。本工程的**显示、外设收发、时钟实际频率均未上板验证过** ——
除非你真的插着探针跑过 `fw.py verify`。

### 3.4 失败要认

判断错了就直接说，不粉饰。**不要把"我推断"写成"实测"** ——
两者的可信度差一个数量级，混在一起会让后面所有基于它的判断都错。

## 4. 冲突时的优先级

```
安全（本篇） > 分层（docs/01 的 R1~R4） > 风格（docs/08 / 09）
```

**举例**：

- 规矩 1（不跳层）与"快速修一个 bug"冲突 → 遵守规矩 1，哪怕多写一层转发。
- 零告警门禁与"加个 `-Wno-` 先让它过"冲突 → 遵守门禁，或说明理由后由人拍板。
- 任何规矩与"要动工程外的东西"冲突 → 停下来问人。

---

## 5. 需要人确认时，怎么问

**不要问"要不要继续"** —— 那是把判断推回给人。

要问的是**具体选项**：

```
❌ "改时钟树有风险，要继续吗？"
✅ "HSE 实测是 8MHz，但 board_config.h 写的是 25MHz（两者矛盾，fw.py lint 会报）。
   两条路：
   A. 按 8MHz 改 board_config.h 与 .ioc 的 RCC.PLLM（推荐，与 main.c 的 PLLM=4 一致）
   B. 你的板子上其实是 25MHz 晶振 → 改 .ioc 的 RCC.HSE_VALUE 与 PLLM=25
   我倾向 A，因为 main.c 里 CubeMX 生成的 PLLM=4 是按 8MHz 算的。选哪个？"
```

**判据**：给出的选项里，**每个都要是你真的能执行的**，并且说明你倾向哪个、为什么。
