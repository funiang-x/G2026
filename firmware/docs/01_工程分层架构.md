# 01 — 工程分层架构

> 状态：**已定稿**（2026-09-21）
>
> 骨架 `AGENTS.md` §2 的 R1 / R2 / R3 细则。**动手写代码前先读这篇。**

## 为什么分层

一句话：**为了让业务逻辑能在电脑上测。**

`Operation/` 只吃数字、吐数字，不碰硬件也不碰 RTOS —— 所以它能直接用 `gcc` 在 PC 上
编译运行。逻辑错了电脑上就能抓出来，不用烧板子、不用示波器。

分层不是为了好看。**谁在 `Operation/` 里偷用了硬件函数，谁就杀死了电脑测试。**

## 四层

```
Task/                   调度层："什么时候做"（FreeRTOS API 只在这层）
  ↓
Operation/              业务层："产品要做什么"（纯计算，可在 PC 上单测）
  ↓
Device/                 设备层："怎么操作一个硬件"（唯一能用 HAL 的层）
  ↓
Core/ + Drivers/        CubeMX 生成 + ST HAL + CMSIS（不改）

Common/                 横切：日志 / 错误码（谁都能用，自身零依赖）
project_config.h        应用参数：周期 / 阈值 / 开关（不含任何 HAL 内容）
```

| 层 | 目录 | 只做一件事 | 允许 include | **禁止** |
|---|---|---|---|---|
| 调度 | `Task/` | **什么时候做** | `Operation/Inc`、`Device/Inc`（仅组合根）、FreeRTOS、`project_config.h` | 把业务算法写在这里（那是 Operation 的事） |
| 业务 | `Operation/` | **产品要做什么** | `Operation/Inc`、`Common/Inc`、`project_config.h`、C 标准库 | **HAL / FreeRTOS / `Device/` / 任何 `bsp_*`** |
| 设备 | `Device/` | **怎么操作一个硬件** | `Device/Inc`、`Common/Inc`、HAL、FreeRTOS（中断投递）、`board_config.h` | 业务逻辑（阈值、状态机、协议） |
| 生成 | `Core/` + `Drivers/` | 启动、时钟、中断向量、HAL / CMSIS | — | **手改非 `USER CODE` 区** |
| 横切 | `Common/` | 日志、错误码 | **只有 C 标准库** | 依赖任何一层 |

依赖方向**只能向下**；`Common` 横切四层。

---

## 规矩 1：只能上层调下层，不能跳层

`Task` 调 `Operation`，`Operation` 调 `Device`。
**不能倒过来，也不能跳过** —— `Task` 直接调 `Device` 也不行，哪怕它"只是开个灯"。

> **代价要认**：一个简单动作要多走一层转发。这条买的是"业务逻辑可测"，值。

唯一允许同时看到两侧的地方是**组合根**（见下）。

## 规矩 2：`Operation/` 不许碰硬件、不许用 FreeRTOS

不许出现 `HAL_*`，也不许出现 `vTaskDelay` 这类符号。

需要时间？**让 Task 把"现在过了几毫秒"当数字传进来**：

```c
/* Operation/Inc/op_blink.h —— 纯函数，时间是参数
 * ★ 下面这条是**本工程真实存在**的声明（不是示意），可直接照抄形状。 */
bool op_blink_step(op_blink_t *ctx, uint32_t now_ms);
```

需要共享状态？**不要在 Operation 里加锁**（锁属于 RTOS）。两种做法：

1. 把锁作为**函数指针注入**（Task 层装配时传真锁，PC 测试时传空实现）；
2. 或用 C11 `stdatomic.h` 做无锁双缓冲 —— 原子操作属于 C 标准库，不违反规矩 2。

> **这条是"电脑上可测"的钥匙。** 新增业务逻辑的默认动作是：
> ① 在 `Operation/` 写纯函数 → ② 在 `Test/` 写单测 → ③ `python Tools/fw.py test` 看结果
> → ④ 都过了再接到 `Task/`。**不要**先接硬件再调试。

## 规矩 3：中断代码放 `Device/`，用"投事件"通知上层

中断服务程序写在 `Device/` 里（`HAL_xxx_Callback` 也放那里）。它**不直接调业务**，
而是往队列投一条事件；`Task/` 从队列取出后再调 `Operation/`：

```c
/* Device/Src/bsp_xxx.c —— 中断只干这一件事
 * ⚠️ 下面用 xxx 占位：本工程**当前没有**队列型中断（bsp_gpio / bsp_tick 都没有
 *    ISR），所以这里是**示意**。照抄时把 xxx 换成你自己的模块名。 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *h) {
    uint8_t b = s_rx_byte;
    BaseType_t woken = pdFALSE;
    xQueueSendFromISR(s_uart_evt_q, &b, &woken);   /* 只投递，不跑业务 */
    portYIELD_FROM_ISR(woken);
}

/* Task/Src/app_xxx.c —— 取出来再交给 Operation */
if (xQueueReceive(s_uart_evt_q, &b, portMAX_DELAY) == pdTRUE) {
    op_xxx_feed(&s_parser, b);
}
```

> ⚠️ **别在中断里直接调 `Operation/`。** 长耗时、优先级反转，而且 ISR 里只能用
> `...FromISR()` 系列 API —— 在中断上下文跑业务是嵌入式最常见的一类"偶发故障"。
>
> ⚠️ 顺带一条硬规定：**`Operation/` 只在 Task 上下文被调用**（它不能加锁，
> 因为锁属于 RTOS）。这条保证它不需要重入保护。

## 规矩 4：CubeMX 生成的代码只在 `USER CODE BEGIN/END` 之间写

那两个标记以外的地方，CubeMX 一重新生成就会覆盖。

**本工程的 CubeMX 链路与参考工程不同 —— CubeMX 直接生成到工程根**（不是沙盒）。
所以规矩 4 在这里展开成三条禁令：

| # | 禁令 | 覆盖后会怎样 |
|---|---|---|
| 4a | 不在 `Core/` 下非 `USER CODE` 区写代码 | **没有报错**，你写的代码静默消失 |
| 4b | 不手改 `Drivers/`（HAL / CMSIS） | CubeMX 重新生成时被还原 |
| 4c | 不手改 `cmake/stm32cubemx/CMakeLists.txt` | 同上（它是每次生成的源码清单） |

**允许手改的两个生成物**（已实测不会被覆盖）：

- `CMakeLists.txt`（顶层）—— CubeMX 只在**第一次**生成，之后不覆盖；
- `CMakePresets.json` —— 同样不覆盖。

**具体约定**：

- `Core/Src/main.c` 的 `USER CODE BEGIN 2` 里**只写"启动 Task 层"**（`app_init()`），
  业务一行都不要进 `main.c`；
- **MSP 归生成物**：`Core/Src/<外设>.c` 里的 `HAL_xxx_MspInit/MspDeInit` 由 CubeMX
  生成（引脚 / 复用 / 时钟都在里面）。`Device/` **不要**自己再定义一份 ——
  实测会 `multiple definition` 链接失败。理由见 `docs/11` §3；
- `Core/Src/stm32f4xx_it.c` 里放 `HardFault_Handler` 的取证调用与各外设中断转调；
- **任务不用 CubeMX 的图形界面建**（那样任务会落在生成物里）。⚠️ 但实测
  CubeMX **会强制重建 `defaultTask`** ⇒ 本工程的做法是
  「CubeMX 建空壳任务 + 循环体写在 `Task/Src/app_rtos.c`」，详见 `docs/11` §3。

## 规矩靠什么强制（不靠自觉，也不写检查器）

| 规矩 | 强制手段 | 失效时会怎样 |
|---|---|---|
| 2（不碰硬件/RTOS） | `operation` 目标**只链 `common`** ⇒ 拿不到那些 include 路径 | 编译期直接报 `fatal error: stm32f4xx_hal.h: No such file` |
| 2（防绕过） | **PC 侧构建**（`fw.py test`）里没有 HAL / FreeRTOS 符号 | 链接期报 `undefined reference to vTaskDelay` |
| 2（可测试性） | `Test/` 用 host 编译器编**同一份源码** | 编不过就说明 Operation 里混进了硬件依赖 |
| 1（不跳层） | ⚠️ **CMake 管不了**（它只有目标级粒度） | 靠本文件 + review |
| 4（USER CODE） | 靠理解 CubeMX 的行为 | ⚠️ 覆盖后**没有报错**，只是你写的代码没了 |

> ⚠️ **规矩 2 的强制有边界**：刻意绕过能过 MCU 侧 —— 自己写
> `extern void vTaskDelay(unsigned);` 再调用，编译链接都过，因为最终固件本来就链了 FreeRTOS。
> 那种写法由 **PC 侧**拦住（`undefined reference`）。
>
> ⇒ **两道墙合起来才完整**，这也是"Operation 必须能在 PC 上编过"的另一层价值。
> `python Tools/fw.py selftest --full` 会逐条验证这两道墙（含注入真违规的负向用例）。

## 唯一允许跨层的地方：组合根

`Task/Src/app.c` 是**组合根**（Composition Root）—— 它同时看 `Operation/` 与 `Device/`，
职责只有三件事：**创建实例 → 注入参数 → 启动任务**。

```c
/* Task/Src/app.c —— 装配，不是业务
 * ★ 下面三行是**本工程真实的 app_init() 内容**（见 Task/Src/app.c），可直接对照。 */
bsp_log_init();                                          /* Device：日志后端就位（最先） */
app_blink_init(APP_BLINK_ON_MS, APP_BLINK_OFF_MS);        /* Operation：参数注入 */
(void)bsp_gpio_config_out(s_led);                        /* Device：把结论落到硬件 */
```

> ⚠️ 装配与**启动**是分开的：`app_init()` 在 `main()` 的 `USER CODE BEGIN 2` 里被调，
> 那时**调度器还没启动**（详见 `Task/Inc/app.h` 的时序说明）；
> 任务体在 `Task/Src/app_rtos.c` 的 `app_rtos_run()`，由 `Core/Src/freertos.c`
> 的 `StartDefaultTask` 调（那是生成物里唯一的胶水行，见 `docs/11` §3 的说明）。

> 为什么必须有它：装配逻辑天然要同时看到两侧，否则"谁把 Device 交到 Operation
> 手上"就没地方放。它是**装配**，不是业务 —— 业务代码仍然不能跳层。
>
> ⚠️ 除它之外，`Task/` 里的其它文件**只 include `Operation/Inc`**。

## 各层怎么写（速查）

| 你想做的事 | 写在哪 | 怎么验证 |
|---|---|---|
| 加业务逻辑（阈值判断、协议解析、状态机） | `Operation/Src/op_xxx.c`（纯函数，时间与数据都是参数） | 先在 `Test/test_op_xxx.c` 写单测 → `python Tools/fw.py test` |
| 加周期任务 / 调优先级 / 改栈深 | 已有任务（`defaultTask`）的参数在 `.ioc` 的 `FREERTOS.Tasks01`；**加新任务**写 `Task/Src/app_rtos.c` + 参数进 `project_config.h` | `python Tools/fw.py build --clean-first`（零告警） |
| 加一个硬件驱动 | `Device/Src/bsp_xxx.c` + `Device/Inc/bsp_xxx.h`，并在 `Device/Inc/bsp.h` 加一行 include | 上板 `python Tools/fw.py verify` |
| 加一个中断 | `Device/Src/bsp_xxx.c` 里写回调 + 投队列；`Core/Src/stm32f4xx_it.c` 的 USER CODE 段转调 | 上板 |
| 改引脚 / 时钟 | `Core/Inc/board_config.h` + CubeMX 的 `.ioc`（**两处都要改**，否则 `fw.py lint` 报矛盾） | **必须重新上板验证** |
| 改周期 / 阈值 / 功能开关 | `project_config.h`（工程根） | 看它被谁用到 |

## 常量放哪

- **硬件事实**（引脚 / 时钟 / 分辨率 / DMA 通道）→ `Core/Inc/board_config.h`
- **应用参数**（周期、阈值、功能开关）→ `project_config.h`（工程根）
- 两处都**不要**在 `.c` 里散落魔法数字。
- ⚠️ `project_config.h` 里**不许出现 HAL 内容** —— 它会被 `Operation/` include，
  一旦引了硬件宏，Operation 在 PC 上就编不过。

## 本工程的分层落地情况

**已完成**（2026-09-21）。`Operation/Src/op_blink.c` 是**已经跑通**的样板：
它有一条 PC 单测（`Test/test_op_blink.c`，`fw.py test` 通过），
因此规矩 2 的两道墙都处在**被验证**的状态（`fw.py selftest --full` 会复验）。

新增业务逻辑时照它的四步走（`docs/10` §A）：
`op_xxx.h/.c` 纯逻辑 → `Test/test_op_xxx.c` 单测 → `Task/Src/app_xxx.c` 适配器 →
在组合根 `Task/Src/app.c` 里装配。
