> **被评估对象**：CSDN 博客《STM32F4标准库下，用DMA+FSMC驱动TFT屏，让你的LVGL界面刷新快人一步》

> **三态口径**（沿用工作台铁律 1）：本文每个数字分三类 ——

> 凡"某方案能带来多少收益"一律是**上限推算**，不是实测；未做过的实现细节不作承诺。

> ## ★★ v1.1 修订（2026-10-14 同日，触发 = 用户现场观察）
>
> **用户观察**：「全屏滑动的时候，屏上那个控件（sysmon 的 CPU%）也达到了接近 100。」
>
> **v1.0 错在哪**：它把"DMA 收益上限"锚在**静屏**负载（59 kpx/s ⇒ 0.59%），
> 又把"极端上界"锚在 **10 Hz** —— 那是**数据率**（`APP_MEAS_PERIOD_MS`），
> 而全屏滑动时每个动画帧**整屏 153,600 px 全脏**、动画帧率是 **~50 fps** ⇒ **低估 5 倍**。
> ⇒ 正确的滑动口径是 **flush 占墙钟 59~77%**（§5.1）。
>
> **本节以下结论一律以"分场景"为准**（静屏 / 全屏滑动），不再有单一的"收益上限"。

> ## ★★ v1.2 实测裁决（2026-10-14 同日，触发 = 用户按 C4 抓回的 RTT）
>
> **v1.1 的 59~77% 也被实测推翻 —— 这次错在"帧率"**：v1.1 沿用项目文档的"滑动 ~50 fps"估计，
> 而**实测滑动只有 7~16 fps**。实测结果（§5.6）：
>
> | | flush÷handler | handler 占墙钟 |
> |---|---|---|
> | 静屏 | 1.5% | 29.7% |
> | 滑动（最快那一窗） | **26.0%** | **87.6%** |
>
> ⇒ **滑动的主成本是软件渲染（64.8% 墙钟），写屏只占 22.8%** ⇒ **裁决：不做 DMA**
> （理由**换了**：v1.0 说"flush 太小"用的是静屏口径；实测说"**写屏只占 23%、渲染占 65%，且双缓冲装不进 RAM**"）。
> ⇒ **下一个靶子是渲染侧，而且已有具体嫌疑人**：滑动时 **LVGL 堆近乎耗尽**（`heap free` 1910 → 189 → **1**，静屏 19100）。

> ## ★ v1.4 候选人被否（2026-10-14 同日，触发 = 用户烧了 C5 的 B 版）
>
> **C5 的嫌疑人被 A/B 证伪并已回退**（§5.7）：把 `LV_DRAW_LAYER_SIMPLE_BUF_SIZE` 从 24 KB 改到 8 KB，
> 上板读数**逐项相同**（`heap free` 1 B / `handler` 88.6% / 16.2 fps / `flush÷handler` 25.9%）。
> **原因查清了，不是"改了没用"，是"这条路径根本没被走到"** —— 该宏只对 `style_opa<255` / 非 NORMAL blend 生效，
> 而本 UI **只有 `bg_opa` / `border_opa`**、**没有任何触发 simple layer 的控件** ⇒ 它是**死配置**。
>
> ⇒ **下一个动作不是"照 `heap free` 去调池"，而是先确认那个读数是不是真的（§6.2 C6）**：
> 若真只剩 1 B，下次分配必然失败并打 ERROR，而**整份日志 0 条 `[E]`/`[W]`**。

## §0 一句话结论（**v1.2：以上板实测为准**）

**博客 9 条里，本工程"已做且更深"3 条、"不适用/有害"4 条、"条件采纳"2 条。**

**实测裁决（§5.6，2026-10-14）——两个场景的 `flush ÷ handler`：**

| 场景 | `flush` 占墙钟 | 写屏 ÷ handler | 谁是大头 | 裁决 |
|---|---|---|---|---|
| **静屏**（页 0 + 悬空） | 0.44% | 1.5% | 渲染 | **不做 DMA** |
| **全屏滑动**（最快一窗，16.2 fps） | **22.8%** | **26.0%** | **软件渲染 64.8%**（写屏 22.8%） | **不做 DMA；转渲染侧** |

⇒ **主结论（v1.2）**：
1. **不做 DMA**（三个版本的理由不同，见 §8：v1.0 用静屏口径、v1.1 用推算、**v1.2 用实测**）。
   实测依据：滑动里**渲染是写屏的 2.8 倍**（每帧 `render ≈40.0 ms` vs `flush ≈14.1 ms`）；且**双缓冲装不进 RAM**（§5.5 ②）。
2. **两个场景都不是"写屏瓶颈"** ⇒ 博客 B2/B3/B4/B5 在本工程**始终不适用**。
3. **滑动确实是残留缺口**（帧率 7~16 fps、sysmon CPU 87.6%、`>33 ms` 掉帧桶占 10~18%），
   但**该啃的是渲染**（每帧 render 40 ms vs flush 14 ms）。
4. **两个候选靶子已被否掉**：`LV_DRAW_LAYER_SIMPLE_BUF_SIZE` 是**死配置**（A/B 逐项不变，§5.7）；
   "**滑动把 LVGL 堆吃干**"是**日志截断造出来的假象**（真值一直 18.9 KB 空闲，§5.9 A）。
5. **★ 新发现的第三个靶子（也是本轮最有价值的）**：滑动窗口回归给出
   `handler = 38.0 ms/帧 × 帧率 + 253 ms/s` —— 那 **253 ms/s（25.3% CPU）与画了几帧无关**，
   而且**静屏时也在**（**静屏 `handler 29.7%` 几乎全是它，不是渲染**）
   ⇒ 新登记 **C7**（§5.9 B / §6.2）。**它之前从来没被看见过。**

**最硬的一条论据**：博客自报"DMA 方式整屏 8 ms"（320×240）⇒ **9.6 Mpx/s**；
而本工程**没有 DMA 的 CPU 直写**实测 **100 ns/字 ≈ 10 Mpx/s**（`bsp_lcd.c:91`）——
**本工程现有的直写实现，已经达到了该文 DMA 方案的吞吐水平。**
该文真正的收益来自"把逐像素函数调用的写法换成批量搬运"（其"传统方式"隐含 ≈0.38 Mpx/s），
那一步本工程在 2026-10-13 之前就跨过了。

## §2 被评估方案（逐条拆解）

原文以 ILI9341 + STM32F4 **标准库**为背景，共 9 条可操作内容：

| # | 博客的主张 | 原文关键参数 |
|---|---|---|
| B1 | FSMC 时序优化 | `AddressSetupTime=1 / AddressHoldTime=0 / DataSetupTime=5 / AccessMode A`；建议逻辑分析仪微调 |
| B2 | DMA2 引擎调优 | `DMA2_Stream3`、`MemoryToMemory` 方向、`PAR=源`、目标固定 `&LCD->RAM`、HalfWord、Normal、`Priority_High`、`FIFOMode_Enable`、`FIFOThreshold_HalfFull`、`MemoryBurst_INC4`、`PeripheralBurst_Single`、开 TC 中断 |
| B3 | `LCD_DMA_Transfer(x1,y1,x2,y2,color)` 封装 | 开窗 → 关 DMA 并等 `DISABLE` → 设 `NDTR`/`PAR` → 清 TC → 使能 |
| B4 | **异步 flush** | `disp_flush` 发起 DMA 后**不立即**调 `lv_disp_flush_ready`，改到 **DMA 完成中断**里调（让 CPU 在搬运期间渲染下一块） |
| B5 | **双缓冲 + 局部缓冲** | `buf1/buf2` 各 `LCD_HOR_RES*10`，`lv_disp_buf_init()`；文中提示"频繁更新小区域时用双缓冲避免等 DMA" |
| B6 | 性能监控 | `#define LV_USE_PERF_MONITOR 1` |
| B7 | 实测收益表 | 静态 42→45 fps · 列表 18→36 · 复杂动画 9→24 · 全屏渐变 5→18；CPU 最高 97%→41% |
| B8 | 常见问题排查 | 花屏三因（FSMC 时序不匹配 / DMA 传输未完成 / 缓冲区地址需 4 字节对齐） |
| B9 | DMA 性能检查清单 | 最高优先级通道 / 启用 FIFO / 验证内存突发 / 测总线带宽利用率 |

> ⚠️ 原文自身的一处技术提示（抓取时即已标注）：B2 把 DMA 方向写成 `MemoryToMemory`、同时把**源地址写进 `PAR`**、目标固定为 `&LCD->RAM` —— 与"内存→外设"的常规写法在语义上交叉。**照抄前必须按其标准库版本核对**：本工程用的是 HAL（`HAL_SRAM_Init` + FSMC 写窗口），DMA 侧要走 `DMA_MEMORY_TO_PERIPH`（外设侧 = FSMC 数据窗口地址、不自增；内存侧 = draw buffer、自增）。

另有一条原文**未涉及**：编译选项（Keil/IAR/GCC 优化等级、`.ramfunc` 段）。本工程的实际取值见 §3.2。

### 3.3 三条硬约束（决定任何外部方案能不能落）

1. **采样窗静默（O1）**：engine 采样窗 2.048 ms 内 FSMC 一次都不许动，靠 `bsp_lcd_bus_take/give` 的**块级**互斥落地（engine 开采集前 take、采完 give；写屏侧每 1024 px take/give 一次）。见 `bsp_lcd.h:92-109`、`app_engine.c:142`、`project_config.h:115-133`。
2. **本屏每收到一次 `0x2C` 就把写地址复位到窗口起点**（2026-10-12 上板实测）⇒ 一次窗口只许发一次 `0x2C`，分块续写必须走 `_cont` 版本。见 `hardware/65`、`bsp_lcd.c:147-158`。
3. **内存余量 ≈10.4 KB**（门禁 120 KB − 实测 112,272 B）⇒ 任何"再加一块缓冲"的想法都要先过这笔账。

### 3.4 顺带查清：sysmon 那个 CPU% 量的是什么（用户的判据锚在它身上）

```
lv_timer.c:131    state_p->busy_time += lv_tick_elaps(handler_start);   /* 每次 handler 返回，累加整段墙钟 */
lv_timer.c:134    state_p->idle_last = (state_p->busy_time * 100) / idle_period_time;  /* busy% */
lv_timer.c:135    state_p->idle_last = ... ? 0 : 100 - state_p->idle_last;             /* 转成 idle */
lv_sysmon.c:273   info->calculated.cpu = 100 - LV_SYSMON_GET_IDLE();                  /* 屏上显示的就是 busy% */
```

⇒ **它 = `lv_timer_handler()` 的累计墙钟 ÷ 窗口墙钟**。而本工程的 **flush 回调（CPU 直写 FSMC）就在 handler 里面**
⇒ **这个数含写屏，且不区分"渲染"与"写屏"**。
⇒ 所以"滑动时它接近 100"的含义只是"**UI 任务被 handler 占满、没时间睡**"；
**不能**据此判断是渲染慢还是写屏慢 —— 要分解必须看 `[LVGL] diag` 的 `flush µs` 与 `handler µs`（§6.2 C4）。

## §4 逐条判定

判定用词：**已做**（本工程已实现且更深）/ **不适用**（前提不成立）/ **不采纳**（有害或收益不划算）/ **条件采纳**（登记，需人拍板）。

| # | 判定 | 依据（量化） |
|---|---|---|
| B1 FSMC 时序 | **不采纳（照抄会违规）** | 原文 `AS=1/DS=5` ⇒ 7 HCLK = **48.6 ns**（本工程 144 MHz）⇒ **低于本屏 TWC(min) 66 ns**（`board_config.h:481-482` 引屏 spec §7.4.1），更是远低于现有 76.4 ns 的 16% 余量。本工程现行值是按"33Ω 串阻 + 排线负载"留余量后定的（`board_config.h:477-480`）。**提速正路是扩展模式，但属 `.ioc`（人做）** ⇒ 见 §6-C1 |
| B2 DMA 引擎配置 | **写法存疑，不能照抄** | `MemoryToMemory` + 源写 `PAR` + 目标 `&LCD->RAM` 的语义交叉（见 §2 注）。本工程若做须走 `MEMORY_TO_PERIPH`：外设侧 = FSMC 数据窗口（不自增）、内存侧 = draw buffer（自增）。资源上空闲流充足（DMA2_Stream1~7 全空，`adc.c:111` 只占 Stream0） |
| B3 `LCD_DMA_Transfer()` 封装 | **已做（等价物）** | 本工程 `bsp_lcd_write_pixels()` / `_cont()` 就是它的等价物，且**多解决了一件事**：本屏的 `0x2C` 复位问题（原文"每块重设窗口"的写法在本屏会**整屏雪花**，2026-10-12 已实测踩过 —— `hardware/65`） |
| B4 **异步 flush** | **不采纳（与线程模型冲突）** | 收益 = flush 那点时间（§5.1 实测上限 0.6%）；代价 = 必须在 **ISR/另一上下文**里调 `lv_display_flush_ready()`，而本工程 `LV_USE_OS = LV_OS_NONE` 的契约是"LVGL 只能单任务访问"（`lv_conf.h:125-135`，且该契约有 BASEPRI 死链的历史教训）。详见 §5.4 |
| B5 **双缓冲 + 局部缓冲** | **不适用** | ① 双缓冲的收益**完全依赖 DMA** —— 单核上"渲染"与"同步写屏"用的是同一个 CPU，没有并行可言；② 前提是"传输是瓶颈" —— **静屏下不成立（0.59%）**，但**滑动下成立（59~77%，见 §5.1）⇒ 这一条在滑动口径下要重判**；③ 内存不允许：两块 `480×56×2` = 105 KB > 余量 10.4 KB（§5.5）；④ 本工程已是 PARTIAL 单缓冲 + 1024 px 分块，`s_draw_buf` 就在 SRAM1（DMA 可访问）—— 这条**为将来预留的口子已经留好了**（`app_lvgl.c:14-17`、`project_config.h:51-53`） |
| B6 `LV_USE_PERF_MONITOR` | **已做且更细** | 本工程 = `LV_USE_SYSMON=1` + `LV_USE_PERF_MONITOR=1`（产品要求，右下角浮层），另有**三处自建可观测量**：`[LVGL] diag`（窗口 ms / px / px·s⁻¹ / flush µs / handler µs / 堆）、`[UI] 1s`（刷新次数 / 最大间隔 / **间隔分布** / 分段 等待·业务·LVGL）、顶栏等效 fps。见 `lv_conf.h:1124-1160`、`app_lvgl.c:628-655` |
| B7 实测收益表（2~3× 帧率） | **不可移植** | 该表的对照基准是"**逐像素绘制**"（其自报 320×240 全屏 200 ms ⇒ 隐含 **0.38 Mpx/s**）。本工程直写实测 **10 Mpx/s** —— 比其基准快 **≈26×**，且已等于其 DMA 方式（9.6 Mpx/s）。**收益来源（消除写屏瓶颈）本工程早已拿到**，剩下的天花板只有那 0.6~4% |

## §5 总判定：DMA 化的收益上限（量化）

### 5.1 上限怎么算（**v1.1：分两个场景**）

**场景 A —— 静屏（页 0 + 输入悬空，已实测）**

```
实测写吞吐        = 100 ns/px                      （bsp_lcd.c:91，已实测）
静屏写屏负载      = 59,395 px/s                    （11:12 上板日志，已实测）
⇒ flush 占用      = 59,395 × 100 ns = 5.94 ms/s ≈ 0.59% CPU
历史窗口同量级：3.9%（_work/lvgl_perf_20261014/帧率与波形流畅度-优化方案.md:41）
               · 1.8%（_work/lvgl_perf_20261014/外部文章对照-多核并行渲染.md:57）
```

**场景 B —— 全屏滑动（推算；本工程已有独立的成本模型）**

```
滑动 = 滚动整个 tileview ⇒ **每个动画帧整屏 480×320 全部变脏**
                （_work/lvgl_perf_20261014/滑动流畅度优化方案.md:10-17）
整屏像素        = 480 × 320 = 153,600 px
每帧 flush      = 153,600 × 100 ns = **15.36 ms**（按实测吞吐）
                （按理论时序 76.4 ns/字 则 11.74 ms —— 同上文 :24）
动画帧率        ≈ **50 fps**（该文 §1 的物理上限估计；**注意它 ≠ 10 Hz 数据率**）
⇒ flush 占用    = 15.36 ms × 50 /s = 768 ms/s = **76.8%**（理论时序口径 58.7%）
⇒ 剩给软件渲染  = 23~41% ⇒ UI 任务被占满 ⇒ **sysmon 显示接近 100** ✔（与现场观察一致）
```

| 场景 | 每秒送屏像素 | `flush` 占墙钟 | 性质 |
|---|---|---|---|
| A 静屏 | 59,395 px/s | **0.59%** | 已实测 |
| B 全屏滑动 | 7.68 Mpx/s | **59~77%** | 推算（本工程成本模型） |

**⇒ 更正 v1.0 的锚点错误**：v1.0 把极端上界写成"整屏每次都重绘 **@10 Hz** ⇒ 15.4%" ——
10 Hz 是**数据率**（`APP_MEAS_PERIOD_MS`），而滑动的**动画帧率**是 ~50 fps ⇒ **低估 5 倍**。
⇒ 正确的上界是 **59~77%**。（教训已登记进 §8。）

**⇒ DMA 化的收益上限 = `flush` 的全部时间**：静屏 **0.59%**（可忽略）· 滑动 **59~77%**（不可忽略）。

**★ 而且滑动场景下 DMA 不只是"省 CPU"，还能提帧率**：现在"渲染"与"写屏"在**同一个 CPU 上串行**
（单块 draw buffer + 同步写）⇒ 每帧墙钟 = `渲染 + 写屏`；若用 DMA + **双缓冲**，每带变成
`max(渲染, 写屏)` ⇒ 帧时间的**理论上界 = (渲染+写屏) ÷ max(渲染,写屏) 倍**，
写屏占 59~77% 时约 **1.5~2×**。**这是本次评估里唯一"帧率真能涨"的场合。**

> 附带一笔账：实测 **100 ns/px** 而理论总线只要 **76.4 ns/字** ⇒ 那多出来的 24% 是**循环与 AHB 开销**
> （`bsp_lcd.c:91` 的注释）。DMA 能吃掉这部分——**但**字节序交换若回退成软件预交换，等于把这笔开销换个地方付（§5.3）。

### 5.2 三笔代价（都要在真做之前付）

| 代价 | 具体是什么 | 出处 |
|---|---|---|
| **跨上下文碰 LVGL** | 异步 flush 要求 ISR 调 `lv_display_flush_ready()`；本工程契约是"LVGL 只能 UI 任务访问"（`LV_USE_OS = LV_OS_NONE`）。要么破契约，要么改回 `LV_OS_FREERTOS` 并把 LVGL 初始化挪到调度器之后（有历史死链：`lv_conf.h:125-135` 记录过"BASEPRI 被钉住 → 时基与 ADC DMA 中断全失效"） | `lv_conf.h:125-135` |
| **分块中断** | 采样窗静默要求 1024 px 粒度的 take/give（`project_config.h:115-133`）。DMA 化后"块完成"事件要从 **DMA TC 中断**里拿，即把现在 6 行循环的分块逻辑搬进 ISR —— 复杂度上移，且是**采样窗静默这条硬约束的核心路径** | `app_lvgl.c:134-166` · `bsp_lcd.h:92-109` |
| **字节序改造** | F407 的 DMA **没有字节交换**功能；本工程靠"渲染原生 RGB565 + 搬运循环里交换"。DMA 化后源缓冲必须已是目标字节序 ⇒ 三条路：① 回退 `RGB565_SWAPPED`；② 加一遍软件预交换（等于现状甚至更贵）；③ 其它。**①是否廉价，本工程内部尚未定案** —— 见 §5.3 | `bsp_lcd.c:170-176` · `app_lvgl.c:479-486` |

### 5.3 字节序：一个**未定案的归因**（写下来供阶段二第一项实测）

本工程内部对 `RGB565_SWAPPED` 的代价有两处**互相矛盾**的记载：

- `app_lvgl.c:479-485` 写：`_SWAPPED` "让 LVGL 在渲染的每一像素上做字节交换/格式转换"，**实测每像素 ~2.2 µs** ⇒ 2026-10-13 六轮改成原生 RGB565。
- 但**七轮基线（即在六轮改完之后）**实测仍是 **≈2.0 µs/px**，且七轮把根因定在"**面积 × 算法**"（`lv_obj` 的 `SIZE_CONTENT` 面积被撑成 465×150、斜线掩膜每段每带一次 `malloc`），并明确"`-O2` 只值 1.2× ⇒ 成本不在指令效率"。见 `_work/lvgl_perf_20261014/帧率与波形流畅度-优化方案.md:45` · `:169-179`。

**源码侧的核查（本次新增）**：LVGL 9.5 对 `RGB565_SWAPPED` **有独立的混合实现**，不是"逐像素转换"的包装 ——

```
firmware/Middlewares/LVGL/src/draw/sw/blend/lv_draw_sw_blend_to_rgb565_swapped.c   1560 行
firmware/Middlewares/LVGL/src/draw/sw/blend/lv_draw_sw_blend_to_rgb565.c           1531 行
```

⇒ 两者同量级；`firmware/Middlewares/LVGL/src/draw/sw/blend/lv_draw_sw_blend.c:186-189` / `:246-249` 按目标格式直接分派到对应的 `..._rgb565_swapped()`。（用全路径写是为了消歧：屏厂 ESP32 例程里另有一份同名文件。）
**即：`app_lvgl.c` 那句"逐像素字节交换/格式转换"在 LVGL 9.5 代码里找不到依据。**

**这条为什么对本文是决定性的**：若"回退 `_SWAPPED`"的真实代价≈0，则 §5.2 的第三笔代价（字节序）**瓦解**，DMA 方案的技术障碍只剩两笔；
若 2.2 µs/px 归因成立，则该路不可行。
**⇒ 阶段二第一项 = 一行 A/B 实验**（把 `app_lvgl.c:486` 改回 `LV_COLOR_FORMAT_RGB565_SWAPPED`、同时把 `bsp_lcd.c:176` 的交换去掉，抓同一组 `[UI] 1s` 分段与 `handler`）。成本极低、判据现成。
（**未验证**：本文不做该实验，也不预设结论。）

### 5.5 ★ 两道新障碍（做 DMA 之前必须先过）

| # | 障碍 | 数字 / 判据 |
|---|---|---|
| **① 渲染 vs 写屏的占比未实测** | 决定"该啃写屏还是啃渲染" —— 这是 DMA 值不值的**唯一判据** | 项目内部两个估算**互相打架**：滑动成本模型说"整屏帧 ≈20 ms 其中 flush 11.74 ms ⇒ 渲染 ≈8 ms"（`滑动流畅度优化方案.md:23-25`）；而波形区实测"≈50 周期/px ⇒ 整屏渲染要 53 ms"。**判据 = 滑动期间 `[LVGL] diag` 的 `flush µs ÷ handler µs`**（§6.2 C4）：>50% ⇒ 写屏瓶颈、DMA 对症；<20% ⇒ 仍渲染瓶颈、DMA 只省那 20% |
| ~~② RAM 装不下标准双缓冲~~ → **v1.6 更正** | "渲染 ∥ 传输"**必须有第二块缓冲**才成立（单缓冲只能等） | **v1.5 之前这里算错了**：正确的算法是"**把现有 56 行换成两块 28 行**" ⇒ `2×480×28×2 = 53,760 B` = **与现在一模一样，零 RAM 增量** —— 我拿"**加法**"去算了一个"**替换**"的问题。**真正的代价换成了"带数"**：每帧 **6 带 → 12 带**，每带固定开销（走一遍对象树 + 开窗 + 抢闸）翻倍，**这个开销没人量过** ⇒ 登记为 C9 的第 ② 道 1 行关（`APP_LVGL_DRAW_BUF_LINES` 56→28 单缓冲即可量）。**好消息**：28 行时一整带只有 **1.34 ms**（480×28×100 ns）< 采样窗 2.048 ms ⇒ 采样窗静默可以**整带抢一次闸**，比现在 1024 px 分块还简单 |

### 5.6 ★★ C4 实测结果（2026-10-14，用户按 §6.2 C4 抓回的 RTT）

**原始数据**（`[LVGL] diag`，同一块板；滑动 = 手指在 3 页之间反复快滑）：

| 窗口 | 时长 | flush | flush 调用 | 整屏帧率 | `flush µs` | `handler µs` | **flush÷handler** | handler 占墙钟 |
|---|---|---|---|---|---|---|---|---|
| ① 滑动（中） | 5000 ms | 3,735,318 px（747,063 px/s） | 213（42.6/s） | 7.1 fps | 350,418 | 2,706,686 | **12.9%** | 54.1% |
| ② 滑动（快） | 5035 ms | 8,094,006 px（1,607,548 px/s） | 343（68.1/s） | 11.4 fps | 758,889 | 3,298,627 | **23.0%** | 65.5% |
| ③ 滑动（最快） | 5006 ms | 12,184,416 px（2,433,962 px/s） | 486（97.1/s） | **16.2 fps** | 1,142,221 | 4,384,969 | **26.0%** | **87.6%** |
| ④ 静屏（对照） | 5000 ms | 228,831 px（45,766 px/s） | 88（17.6/s） | — | 21,802 | 1,483,965 | **1.5%** | 29.7% |

**帧率怎么来的**：所有窗口的"最大 … px/次"都恰好 = **26,880 px = 480×56 = 一个完整带**
⇒ "整屏全脏"成立；一帧 = 6 带 ⇒ 帧率 = flush 调用数 ÷ 6。

**窗口 ③ 拆到"每帧"（全屏一帧 = 153,600 px）：**

```
每帧 flush   = 1,142,221 µs ÷ 81 帧 = **14.1 ms**   ← 与 §5.1 推算的 15.36 ms 吻合 ✔
每帧 render  = (4,384,969 − 1,142,221) ÷ 81 = **40.0 ms**
             ⇒ 40.0 ms ÷ 153,600 px = 0.26 µs/px = **37.5 周期/px @144MHz**
                （与波形区实测的"≈50 周期/px"**同量级** ✔ ⇒ 该成本常数在滑动场景也成立）
每帧墙钟     = 54.1 ms ⇒ 18.5 fps（实测 16.2，差的是调度与其他任务）
```

**⇒ 判据结论（按 §5.5 ① 预注册的规则）**：

| 预注册判据 | 实测 | 结论 |
|---|---|---|
| `flush÷handler` **>50%** ⇒ 写屏瓶颈 | 峰值 **26.0%** | ❌ 不成立 |
| `flush÷handler` **<20%** ⇒ 渲染瓶颈 | 12.9% / 23.0% / 26.0% | ⚠️ **落在 20~50% 灰区，但明显偏渲染侧** |

⇒ **滑动 = "渲染 64.8% + 写屏 22.8%" 的混合，渲染是大头（2.8×）**。

**⇒ 对 DMA 的裁决（实测口径）**：

| 方案 | 帧时间 | 帧率 | 结论 |
|---|---|---|---|
| 现状 | render + flush = 54.1 ms | 16.2 fps（实测） | — |
| DMA **单缓冲**（写屏挪给 DMA，仍串行） | **不涨**（54.1 ms） | 不涨 | CPU 省 22.8%，但**约束是渲染墙钟、不是 CPU** ⇒ 无感 |
| DMA **+ 双缓冲**（渲染 ∥ 传输） | max(40.0, 14.1) = 40.0 ms | **≈25 fps（+54%）** | 有收益，且 **RAM 零增量**（两块 28 行 = 现有 56 行，见 §5.5 ②的更正）；代价 = **带数 6→12 的每带开销**（未量，C9 第②关）+ **字节序**（C9 第①关） |

⇒ **裁决：不做 DMA**。它**能**给约 +54% 帧率，但：① 这笔收益全部来自"渲染 ∥ 传输"的重叠，
而**渲染本身（40 ms/帧）才是更大的靶子** —— 省掉 30% 渲染（12 ms/帧）就约等于它的收益，
**且不必付那三笔代价**；② 双缓冲的 RAM 账不成立。

#### ③ ★ 本轮价值最大的一条新发现：滑动时 **LVGL 堆近乎耗尽**

| 窗口 | `heap free` |
|---|---|
| ④ 静屏 | **19,100 B** |
| ① 滑动（中） | **1,910 B** |
| ② 滑动（快） | **189 B** |
| ③ 滑动（最快） | **1 B** |

32 KB 的 LVGL 主池在滑动时**见底**。最可能的元凶（**待实测，未验证**）：
`lv_conf.h:171` 的 **`LV_DRAW_LAYER_SIMPLE_BUF_SIZE = 24*1024`** —— 只要某个 widget 有
`style_opa < 255` 或非 NORMAL blend，LVGL 就为"simple layer"申请**最高 24 KB** 的临时缓冲，
而池总共只有 32 KB（同时还要放 65 个对象、字体缓存、以及**斜线掩膜** —— 后者在
`_work/lvgl_perf_20261014/外部优化文章对照.md:84-107` 已查明是"每段每带一次 `lv_malloc/lv_free`"）。
⇒ **它很可能同时解释"滑动渲染 40 ms/帧"**：分配失败/碎片化会让渲染走慢路径或反复重试。

**同一份日志里的其它观察**（已登记进 §8）：`>33 ms` 掉帧桶占 10~18% · `发布→重绘 max` 380~441 ms ·
DSP 段被 UI 抢到 19.9 ms · `Task_Ui 栈余量 1124 B`；
**而 `循环 87~117 次/s` 基本维持 ⇒ 排除 L1"UI 循环塌了"的假说**。

1. **该宏对本 UI 是死配置**：`LV_DRAW_LAYER_SIMPLE_BUF_SIZE` 只对"带 `style_opa < 255`
   **或**非 NORMAL blend 的控件"生效（LVGL 自己的注释，`lv_conf.h:165-168` —— **`bg_opa` / `text_opa` 不算**）。
   而本界面全 UI **只有 `bg_opa` / `border_opa`**（`firmware/Task/Src/app_ui.c:324-399`），
   **没有** `style_opa`、**没有** `LV_BLEND_MODE` 非 NORMAL（全仓 grep 0 命中）
   ⇒ **没有任何控件会触发 simple layer** ⇒ 该宏的值不影响任何一帧。
2. 反向也成立：若池真的只剩 **1 B**，下一次分配必然失败、`LV_ASSERT_MALLOC` 会打 ERROR
   （八轮刚修好级别映射，ERROR 现在可见）—— 而**整份日志 0 条 `[E]` / 0 条 `[W]`**。

**处置**：`lv_conf.h:171` **已回退到 24 KB**（上游默认），原地留一条 ★ 注释说明"为什么不用改"。
门禁复跑：`test` 5/5 · `lint` 0 · `build --clean-first` **0 告警 0 错误** · `sizecheck` RAM **112,112 B（85.53%）**。

**⇒ 连带结论：`heap free = 1 B` 这个读数本身可疑**（见 §8）—— 它既解释不了现象，
又与"渲染一直在跑、一条分配失败都没有"矛盾。**下一个动作不该是"照它去调池"，而是先确认它的真伪（§6.2 C6）。**

### 5.8 ★ 顺带发现：滑动期间 **engine 被 UI 饿死**（A/B 两版日志都有）

```
[ENG] 一拍   8 ms（采集 2096 + DSP  6589 + 发布 6）   ← 静止/轻载
[ENG] 一拍 897 ms（采集 2096 + DSP 895099 + 发布 6）   ← 滑动最剧烈那一拍
```

同一份日志里还有 `发布→重绘 max **833 ms**`，以及相邻那一秒
`[UI] 1s: 刷新 1 次 · 循环 53 次/s · 间隔分布 …/**21**`。

**机理**：UI 任务优先级 **26** > engine **22**（`docs/01` 的定稿表），滑动时 UI 任务被 LVGL 占满
⇒ engine 那一拍的**墙钟**被拉到 0.9 s（DSP 本身只算 8 ms，其余全是等时间片）。
⇒ **测量节拍在滑动期间从 10 Hz 掉到 ~1 Hz**，松手后恢复。

**这不是本文的 bug**（优先级是刻意的，2 s 判据仍满足），但它是"**滑动时数据看起来不动**"的直接原因，
而且**与刷屏无关**：即便把写屏全免了，只要渲染还占 65%，engine 照样被压。
⇒ 登记为独立观察（**未验证**其对手感与判据的实际影响）。

### 5.9 第三轮抓数：**两个真结果**（2026-10-14，用户授权烧录后）

#### A. `heap free` 之谜结案 —— 是**日志截断**造出的假象，池从来没被吃干

`firmware/Common/Src/log.c:21` 的 `LOG_LINE_MAX = 160U` 让 `vsnprintf` 把格式串截到 159 B，
而 `[LVGL] diag` 那一行超过它 ⇒ **尾部被静默切掉**。实测证据：那份日志的
**32 条 diag 行全部恰好 137 字符**，`heap free=` 后面是**按剩余长度切出来的前缀**：

| 窗口负载 | 打印出来 | 真实值 |
|---|---|---|
| 静 / 轻 | `heap free=18856 maxbl` | **18,856** |
| 中 | `heap free=1885` / `=188` / `=187` | ~18,8xx 的**前缀** |
| 重（前面字段最长） | `heap free=1` | 同上，只切到第 1 位 |

⇒ **池一直有 18.8~19.0 KB 空闲**。这也是 §5.7 那次 A/B 毫无变化的**真正原因**：被测对象根本不存在。
（同类前科：项目文档记过 `s_flush_px` 报出"超 FSMC 物理上限"的假吞吐 —— 同一个坑。）

**修复（三处，已上板验证）**：
- `firmware/Common/Src/log.c`：**截断留痕** —— 被截断的行尾补一个 `~`（不额外占字节）⇒ 以后"被切一半的数字"一眼可辨；
- `firmware/Task/Src/app_lvgl.c` 的 `[LVGL] diag`、`firmware/Task/Src/app_ui.c` 的 `[UI] 1s`：**各拆成两行**（数字行不许超 160 B）；
- 复抓验证：759 行、**0 行带 `~`**、`堆 free 18996 B` 完整可读、`分段`/`页` 字段全部恢复。

#### B. ★ 滑动的成本模型（31 窗口回归 —— 本轮最有用的结果）

窗口级回归（x = 帧率，y = `handler` µs/s，取 29 个"在滑"窗口）：

```
handler = 38.0 ms/帧 × 帧率  +  253 ms/s
flush   = 14.62 ms/帧 × 帧率   （截距 ≈ −11 ms/s ⇒ 纯按帧计费，模型自洽 ✔）
```

⇒ 拆出**两笔互不相同的成本**：

| 项 | 量 | 说明 |
|---|---|---|
| **每帧渲染** | **38.0 ms/帧** | 与帧率成比例；其中 `flush` 只 14.6 ms |
| **每秒固定开销** | **253 ms/s = 25.3% CPU** | **与画了几帧无关** ← 此前完全不知道的一项 |

**★ 而且这笔固定开销是"常驻"的**：本日志里两个近似静止的窗口（帧率 0.5~0.6、`flush` 仅 3 ms/s）
`handler` 仍是 **257~260 ms/s** ⇒ **前几轮我一直引用的"静屏 handler 29.7%"其实几乎全是它**
（静屏渲染只有几十 kpx ≈ 几 ms/s），**不是渲染**。

**按页分解（滑动窗口）**：页 1（频域）**73.6 ms/帧** > 页 2（参数）56.2 > 页 0（**含波形**）53.9
⇒ **滑动时最贵的不是波形那一页**。与静屏"波形占 93%"**不矛盾但不同**：
静屏那次是"一次大块面积重填"，滑动是"整屏都要重画"，成本被摊平了。

**⇒ 对 DMA 的意义（第三次确认）**：`flush/帧 = 14.6 ms`、`f/h ≈ 19~20%` ⇒
**DMA 的上限仍是那 14.6 ms/帧**，结论不变。

### 5.10 ★★ C7 实测：那 253 ms/s **就是触摸轮询**（23.4% CPU），且 **INT 门的前提已验通过**

#### A. 分离（`APP_TOUCH_ENABLE=0`，已上板）

| 状态 | `handler` | 折算 |
|---|---|---|
| 静屏 · **触摸关** | 95,086 ~ 98,533 µs / 5 s | **1.9 ~ 2.0%** |
| 静屏 · 触摸开 | 1,115,000 ~ 1,134,000 µs / 5 s | **22.3 ~ 22.7%** |
| 滑动 · 触摸开（§5.9 B 的回归截距） | 253 ms/s | 25.3% |

⇒ **那笔固定开销 ≈234 ms/s（23.4%）就是触摸轮询**：100 读/s ⇒ **摊到每次读 2.34 ms**。
⚠️ 项目文档记的是"7 B @ 100 kHz ≈ 0.7 ms" —— **高了 3 倍，这笔账本文没解释**（登记待查）。

#### B. INT 门的前提 —— 已实测通过

把 PC5(TP_INT) 的电平打进 `[TOUCH] 1s`（**只读不驱动**，不影响触摸功能）后抓 45 s：

| 状态 | `INT=` | 观测 |
|---|---|---|
| 抬起 | **1** | 连续 7 行 |
| 按下（含持续 2~5 s 的长按） | **0** | 连续 10+ 行 |

**逐秒 100% 一致、零反例**；且 45 s 里 100 Hz 的读**并没有把 INT 拉高**
⇒ 它是**跟随触摸状态的电平**，不是"读一次就复位"的脉冲。
（`firmware/G2026.ioc` 的 `PC5.GPIO_Label=TP_INT` + `GPIO_Input` + `GPIO_PULLUP` 是它的硬件依据。）

#### C. 三点结论

1. **INT 门是一个"该做"的优化**：静屏 **−22~23% CPU**、零 RAM、纯固件、前提已验。
   落在 `firmware/Task/Src/app_lvgl.c` 的 `touch_read_cb`（PC5 是**面板输出**，只读不驱动）。
2. **但它不是滑动掉帧的主药**：滑动时手指大多贴着屏 ⇒ `INT=0` ⇒ 照读；
   只有"甩动（手指离屏）"那一段省 ⇒ 对滑动的贡献 ≈ **甩动占比 × 23%**。
   它真正的价值是**静屏白烧的 23%** 与 **engine 不再被饿死**（§5.8）。
3. **滑动的下一刀仍是"38 ms/帧 渲染"**（§5.9 B），或"**双缓冲 + DMA**"（§6.2 C9）。

## §8 诚实边界

- **所有"若做 DMA 能省多少"都是上限推算**（用已实测的写吞吐 × 已实测的像素负载），**不是**做了之后的实测。本文**没有**实现任何 DMA 刷屏代码。
- **`hardware/65` 的约束没被验证过在 DMA 路径下也成立**：DMA 化后"一次窗口只发一次 `0x2C`"仍必须遵守 —— 本文只指出约束存在，**未验证** DMA 版本会怎么撞上它。
- **§5.3 的结论是"归因未定案"，不是"归因错误"**：源码侧只证明"存在格式原生的 swapped 混合实现"，**没有**做端到端 A/B；真实代价仍可能是别的环节（例如某些降级路径走 `LV_DRAW_SW_RGB565_SWAPPED_*` 的 `LV_RESULT_INVALID` 回退）。**要定案只能实测（C3）**。
- **§5.4 的 27.8 ns 判断基于屏 spec 与 HCLK 换算**，未查 FSMC 扩展模式下 `NWE` 实际脉宽的完整约束（BTR/BWTR 的 DATAST 与 ADDST 组合）—— 标"待澄清"，不作定论。
- `docs/INDEX.md` 里若干旧行引用的 `hardware/04`、`hardware/33` 等文件当前不在 `hardware/` 目录下（现有物 = `58`~`65`）。本文**只引用当前真实存在的路径**。
- `bsp_lcd.c:161-164` 的注释措辞（"字节序的调整已经在 LVGL 侧做掉了"）与 `bsp_lcd.h:70-73` 的八轮订正（"交换在本层搬运循环里做"）**不一致**；同一段代码两种说法，建议顺手统一（**登记，未改**）。
- **★ v1.0 的一处锚点错误（已在 v1.1 更正）**：v1.0 把"整屏重绘"的极端上界锚在 **10 Hz**（= 数据率 `APP_MEAS_PERIOD_MS`），而滑动的**动画帧率**是 **~50 fps** ⇒ **低估 5 倍**。**教训**：算"重绘负载"时锚点必须是**触发重绘的频率**，不是**数据的更新率** —— 这两者在滑动场景差 5 倍，正是本次翻车的原因。
- **滑动场景的 `flush` 占比是推算，不是实测**：它由"整屏每帧全脏"×"~50 fps"两个前提相乘得到，两个前提都来自本工程自己的成本模型（`_work/lvgl_perf_20261014/滑动流畅度优化方案.md` §1），**没有一个是在滑动期间用 `[LVGL] diag` 量过的** ⇒ 本文标"推算"，实测见 §6.2 C4。
- **"~50 fps 是滑动上限"也是推算**，且它与"波形区 50 周期/px"的成本常数**在同一量级上不自洽**（§5.5 ① 的两个估算打架）⇒ 这正是 C4 存在的理由。**C4 实测（§5.6）已给出裁决：实测 7~16 fps，"50 周期/px"那一支是对的。**
- **★ v1.1 的 59~77% 推算同样被实测推翻（第二次锚点错误）**：这次错在**帧率** —— v1.1 沿用了项目文档的"~50 fps"估计，实测只有 **7~16 fps**（偏乐观 3 倍）。**两次错误合并成一条教训**：算重绘负载的两个乘数（**每次重绘的面积** 与 **触发重绘的频率**）**都必须来自实测**；两个都靠"从文档里挑一个数"，就会连着错两次。**§5.6 是这两个乘数第一次同时有实测值的地方。**

### D. 触摸 I²C 提速到 400 kHz —— **实测不可用，需回退**（2026-10-14 晚）

背景：触摸轮询是**拖动期间**最大的常驻开销之一，而"一次 I²C 读到底多久"在本文件里
一直是谜（早期记 0.7 ms，v1.6 又摊出 2.34 ms）。用户在 CubeMX 把 `hi2c2` 从
**100 kHz 提到 400 kHz**（`Core/Src/i2c.c:41`）后，**用当天新加的 `I2C 读均 X us/Y 次`
探针**实测：

| | 100 kHz（同日，改前） | **400 kHz（改后）** |
|---|---|---|
| `[TOUCH] 1s` 的**失败** | **0** | **27~46 次/秒** |
| 状态 / 坐标 | 正常跟手 | **一直"抬起"、坐标 (0,0)** |
| 单次 I²C 读耗时 | （待重测） | **10,000~16,000 µs** |

⇒ **结论：这颗 FT6336 模块在这块板上跑不了 400 kHz**。`INT=0` 会出现（面板确实在报按下），
但 I²C 读全失败；每次失败走 HAL 的超时/重试 ⇒ 单次读从"百微秒级"涨到 **10~16 ms**，
×40 次/秒 ≈ **40% CPU 白烧**，而触摸**完全不能用**。
**判据（回退到 100 kHz 后必须满足）：`失败 0` + 坐标跟手。**

**原因判断（指向硬件，不是软件配置）**：PCB 评审（`hardware/55-PCB交叉评审…`）
早就点过**触摸 I²C 上拉 `R15/R16` 是 10 kΩ** —— 200 kHz 以上上升沿太慢 ⇒ 波形坏 ⇒ NACK。
⇒ 想真正提速，**先换 2.2k/4.7k 上拉**（硬件改动，记入 PCB 待办），别只改波特率。

⚠️ **同时更正一条口径**：本文件里的"**2.34 ms/次**"很可能就是**在失败重试下**量到的
（正常成功的读应在百微秒级）⇒ **在 100 kHz 下重测之前，该数字不可用于收益估算**
（因此"① 省 14~16% CPU"的**前提不成立**，撤回该估算）。
✅ 探针的价值：这个回归是**它当场抓出来的** —— 没有它，现场只会看到"触摸不灵了"。

#### D-续：触摸读的账被量清了，**修掉 29%**，第二刀失败并已回退（同日，AI 执行）

**先量账**（100 kHz，手指按住）：一次 `bsp_touch_read` = **6.28 ms**，×100 Hz ⇒ **≈63% CPU**
（同一份日志的 `handler 3.41 s/5 s = 68%` **对得上**）。而 100 kHz 读 5 字节的**线时长
只有 ~0.45 ms** ⇒ **≈94% 是"失败后干等超时"**：`bsp_touch_read` 每次做**两个事务**
（`TD_STATUS` 1 B + `POINT1` 4 B）⇒ **两个 5 ms 超时窗口**。
（`bsp_touch.c` 里那句注释"失败率≈45%，超时已收到 5ms ⇒ **代价可忽略**" —— **实测证明是错的**。）

| 改法 | `I2C 读均` | `失败` | 坐标 | 判决 |
|---|---|---|---|---|
| 原始（两次事务 + 超时 5 ms） | **6.28 ms** | 0 | 跟手 | 基线 |
| **两次读合并成一次**（0x02 起连读 5 字节：TD_STATUS + 点1） | **4.45~4.59 ms** | 0 | 跟手 | **✅ 采用（−29%）** |
| 再叠加"超时 5→2 ms" | **9.9~22.8 ms** | **8~17/秒** | **不能用** | **❌ 已回退** |

**第二刀为什么失败（机理，值得记住）**：HAL 在 2 ms 就把传输**中途掐断** ⇒ **总线被留在坏状态**
⇒ 紧接着的"重试一次"也失败 ⇒ 触发本文件的**连续失败退避（100 ms）+ 总线恢复流程**
⇒ 每轮 10~23 ms，**比省下的 3 ms 贵 3~7 倍**。
⇒ **"超时值"不是可以随便拧的旋钮：缩短它会把"慢"换成"坏"。**

**剩下那 4.5 ms 的账**：反推仍有 **≈78% 的调用撞满超时** ⇒ 写屏时 FSMC 的噪声几乎每次都在
打坏一个事务。要再压只剩两条**成本更高**的路（本轮都没做）：
1. **硬件降噪**：加强触摸 I²C 上拉（`R15/R16` 现为 **10 kΩ** → 2.2k/4.7k）+ 去耦
   ⇒ 提高**首次成功率**（这条同时是"想上 400 kHz 就必须先做"的前置）；
2. **交互折中**：按住期间把读周期 10 ms → 20 ms ⇒ CPU 减半（≈22%），代价是**跟手延迟翻倍**。

⚠️ **这一条把优化清单的排序改了**：**"按住时"最大的 CPU 消耗是触摸读（≈44%，合并读之后）**，
不是渲染、也不是写屏。以后讨论"拖动卡"要先看这里。
