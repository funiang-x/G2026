## §2 页面生命周期：怎么做的、为什么这么做

### 2.1 只销毁"内容"，tile 对象常驻

`lv_tileview` 靠 tile 对象算布局与滚动行程（删了会破坏滚动条与坐标），而 tile 只是
3 个空容器；**内容**（17 / 24 / 10 个对象）才是吃池的大头 ⇒ 销毁内容就拿到了全部收益，零风险。
（稳态驻留行里那三个 `FREQ=1 / CAL=1` 就是"空 tile"。）

### 2.2 ★★ 时机是"切换流畅"的全部秘密

- **建得早**：建在 `tile_changed_cb` 里。`lv_tileview` 在**拖动过程中**就会把目标页变成
  "活动页"并发 `VALUE_CHANGED`（这条行为 `app_ui.c` 早就记着）⇒ **手指还没松就开始建**，
  等页真正滑到位时早已建好 ⇒ 看不到空白、也感觉不到停顿（建页耗时见 §4）。
- **删得晚**：离开后**推迟** `APP_UI_PAGE_FREE_DELAY_MS`（500ms）再删 —— 拖动动画期间
  老页仍在屏幕上，立刻删就是半屏空白。
- **先建后删**：反了会有一帧"老页已删、新页没建"的空白。

### 2.3 为什么"删了重建"不丢状态

本文件的页面状态**全在静态 C 变量里**（波形点 `s_wave_pts/y`、1T/3T `s_cycles`、自检表…），
LVGL 对象只是这些数据的**视图** ⇒ 删视图不丢数据。

⚠️ **但"跳过重复更新"的门必须复位**，否则重建出来的新对象不会被灌数据 —— 见
`page_destroy()` 里对 `s_wave_last_n` / `s_wave_dim` 的复位（少了这两行，**波形页重建后永远是空的**），
以及 `page_build(2)` 里对 `cal_sync_selftest()` 的直接调用（自检表是每 N 秒才刷的）。

### 2.4 安全性依据（查过源码/实测，不是推测）

- `lv_obj_delete/clean` 会 `lv_event_mark_deleted()` + `lv_anim_delete(obj, NULL)`
  （`Middlewares/LVGL/src/core/lv_obj.c:590-602`）⇒ **删页时正在跑的滚入/生长动画会被自动清掉**，
  不必手动杀（与 `splash_tap_cb`"在自己回调里删自己"是同一套机制）。
- 标定覆盖层（`s_cal_panel/progress/prompt`）建在**屏幕**上、由 `s_st_wall` 铺满且默认
  CLICKABLE ⇒ 覆盖层显示时**滑不动页** ⇒ 标定期间不可能销毁页 2。
- `set_text()` / `set_hidden()` 加了 **NULL 免疫**（早返回而不是解引用）——
  这是整套懒加载的安全网：与其在 8 个刷新函数里逐个判页面，不如让最底层两个写入口免疫。

### 2.5 ★ 上板实测抓到并修掉的漏洞：单槽 pending 会漏回收

第一版"待销毁"只有一个槽位。**快滑**（0→1→2，每步 <500ms）时后一页的排期会**覆盖**前一页
⇒ 日志里"页 0 建成"之后**没有**"页 0 销毁"，而"页 1 销毁"出现两次 ⇒
**最先离开的那一页永远不会被回收**，直接违背需求 2。

⇒ 改成"**到期就扫描一遍：除了当前页，全部销毁**"。修后无论滑多快，稳态只剩当前页（§4.2）。
（这条只有"快滑"这一个手势能暴露 —— 慢速一页一页翻是看不出来的。）

## §3 LVGL 裁剪

### 3.1 依据（逐条查过，不是猜的）

- 本工程代码只用 **3 种控件**：`lv_obj` / `lv_label` / `lv_line`（+ `lv_tileview`）；
- 12 个"关了会出事"的高危 API **全部 0 处**：`lv_obj_set_flex` / `lv_obj_set_grid` /
  `lv_gridnav` / `lv_image` / `lv_subject` / `lv_observer` / `lv_theme` / `lv_span` /
  `lv_canvas` / `lv_msg` / `lv_fs_` / 图片编解码（bmp/png/qrcode/gif/lottie）；
- `tileview` 与 `lv_obj_scroll` 内部**不用** flex/grid（查过源码）。

### 3.2 关掉的 23 个开关

19 个控件（ARC/BAR/BUTTON/BUTTONMATRIX/CHART/CHECKBOX/DROPDOWN/IMAGE/KEYBOARD/MSGBOX/
ROLLER/SCALE/SLIDER/SPINBOX/SPINNER/SWITCH/TABLE/TABVIEW/TEXTAREA）
+ 2 个主题（THEME_SIMPLE / THEME_MONO；`THEME_DEFAULT` 本来就是 0，见 `app_ui.h` 的跨文件契约）
+ 2 个布局（FLEX / GRID）。

改动是干净的 **23 行**（`diff` 恰好 46 行 = 23×2；脚本用二进制读写，不碰换行符）。

### 3.3 ⚠️ 保留项与一个反例

- **`LV_USE_OBSERVER` 不能关**：屏上那个 FPS/CPU 浮层（sysmon）内部用
  `lv_subject/lv_observer`（`src/debugging/sysmon/lv_sysmon.c:42,50,70,117,119`）。
  **这就是"查了再关"和"猜着关"的区别。**
- 保留：`LABEL` / `LINE` / `TILEVIEW`（界面本体）、`SYSMON`（浮层）、`LOG`（`bsp_log` 后端）、
  `DRAW_SW` / 两个 `ASSERT` / `FONT_PLACEHOLDER` / `ST7796`（屏）。

### 3.4 收益（`build --clean-first`）

| | 改前 | 改后 | 差 |
|---|---|---|---|
| FLASH | 527,916 B | **461,140 B** | **−66,776 B（−12.6%）** |
| RAM | 112,352 B | 112,264 B | −88 B |

（RAM 只降 88 B 是正常的：未实例化的控件类不占池，省下的是**代码**。）

## §4 上板实测（**已验证**）

### 4.1 建页 / 销页 / 回收（每次切页成对出现）

| 页 | 对象数 | 建成耗时 | 本页池占用 | 销毁耗时 | 回收 |
|---|---|---|---|---|---|
| 0 TIME | 17 | 9.4~11.3 ms | ≈3.07~3.11 KB | 1.25~1.37 ms | ≈2.95~3.05 KB |
| 1 FREQ | 24 | 13.3~14.2 ms | ≈4.17~4.26 KB | 1.57~1.71 ms | ≈3.99~4.08 KB |
| 2 CAL | 10 | 7.7~8.0 ms | ≈2.15~2.23 KB | 0.88~1.00 ms | ≈2.03~2.11 KB |

（回收略小于占用 = tlsf 切块与碎片，正常。）

### 4.2 ★ 稳态不变量（需求 1+2 的硬证据）

每次"落定"后的驻留快照，`built` 位图里**永远只有一个 1**，其余页只剩 1 个空 tile：

```
built=0x01 · 对象 TIME=17 FREQ=1  CAL=1     ← 在页 0
built=0x02 · 对象 TIME=1  FREQ=24 CAL=1     ← 在页 1
built=0x04 · 对象 TIME=1  FREQ=1  CAL=10    ← 在页 2
```

连续快速来回滑几十次，**每一份快照都满足该不变量**，0 条 `[E]`。

### 4.3 开机池占用（需求 1 的收益）

| | 改前（三页全建） | 改后（只建首页） |
|---|---|---|
| `[UI] LVGL 堆` | used=16368 · **free=17324** | used=9924 · **free=24580** |

⇒ **开机余量 +7256 B**（原来贴着 2KB 红线，现在 7 KB 富余）。
⚠️ `total_size` 两次读数不一致（34504 vs 33692 B）—— **2026-10-14 结掉一半**：
把 `BOARD_LVGL_MEM_EXT_KB` 从 4 收到 0 之后，`total` **恰好少 4096 B**（34556 → 30460）
⇒ `total` = **各池容量之和**（不是编译期常量里的"36 KB"，池本身有元数据开销）；
剩下的 ~52~812 B 漂移是 **tlsf 按当前切块状态算的**（大块被切开/合并时会变）。
⇒ **口径：凡是比内存余量，一律只看 `free`**（它是唯一直接可比的数），别拿 `total` 做差。

### 4.4 反复建销后池是否恶化（需求 2 的长期面）

约 30+ 次建销后：`heap free` 21.9~27.5 KB、`maxblk` 稳定 **≈20.2 KB**、
`frag` **8%~27% 波动**（无单调上升）⇒ **未观察到泄漏或碎片失控**；
新增的 40% 碎片告警**从未触发**。

## §6 未判定 / 风险（诚实边界）

1. **滑动观感未由人眼判定。** 快滑时 `[UI] 1s` 的 LVGL 分段峰值达 **57~64 ms**，
   其中建页最多 14 ms ⇒ 大头是"整屏滚动重绘"这个 **`03` 已记录的老成本**，不是本次改动引入。
   结论：**本次改动给快滑增加了 ≤14 ms/次 的负载，是否可见未判定**。
   若可见，改法是"更早建"（`LV_EVENT_SCROLL_BEGIN` 时按拖动方向预建邻居）。
2. **长期碎片未测**（只跑了几十次建销，没跑几百次）；40% 告警是护栏，不是结论。
3. **建页那一拍的停顿**（7.7~14.2 ms）藏在下滑手势里 ⇒ 未由人确认"看不见"。
4. `total_size` 两组读数不一致（§4.3）**未解释**。
5. 本文**不涉及** `03` 的刷屏优化结论（DMA 仍未采用）。

## §7 外部资料对照：CSDN《LVGL 页面切换实战：3 种方法对比与 STM32F4 实战》（2026-10-14 追加）

来源：`blog.csdn.net/v6b7n8m9q0/article/details/154715808`（作者 丧尸225，2026-07-18）。
**它讲的正是本文的主题（页面管理）**，所以逐条对照。结论：**只有 1 条可采纳（而且是一条"警告"）**。

### 7.1 它点名的 API / 宏 —— **逐条查过 vendored LVGL 9.5 源码**（这是本节的价值）

| 博客说法 | 源码/本工程实际 | 判决 |
|---|---|---|
| `#define LV_USE_OS_NONE 1` | **不存在该宏**；真名 `LV_USE_OS = LV_OS_NONE`（`src/lv_conf_internal.h:12` 有 `#define LV_OS_NONE 0`）。本工程**本来就是** `LV_USE_OS LV_OS_NONE`（`lv_conf.h:135`） | **已满足**；照抄反而**静默无效** |
| `lv_obj_set_opa_scale(...)` | 9.5 源码里**搜不到**（v8 起移除）⇒ 那段动画代码**编译不过** | 不采纳 |
| `lv_obj_set_parent(obj, NULL)` 表示"脱离对象树" | `src/core/lv_obj_tree.c:147-150` 就是 `LV_ASSERT_OBJ(parent, MY_CLASS)` ⇒ **NULL 非法**，那段"页面对象池"跑不起来 | 不采纳 |
| `LV_MEM_CUSTOM` 替换分配器 | 本工程 FreeRTOS 堆只有 **4096 B**（`Core/Inc/FreeRTOSConfig.h:71`）且用静态分配 ⇒ 换过去会立刻分配失败 | **不采纳（有反证）** |
| `LV_COLOR_DEPTH 16` | 本来就是（`lv_conf.h:41`） | 已满足 |
| `LV_SCR_LOAD_ANIM_FADE_ON` | **存在**，是 v9.2 兼容别名（`src/lv_api_map_v9_2.h:44`）⇒ 这条**不算错**，标准名 `LV_SCREEN_LOAD_ANIM_FADE_ON` | 可用，但**本工程不该用**：全屏 alpha 淡入要整屏混合，`app_ui.c` 文件头早已定案"**不做全屏 alpha 淡出**（8080 直写下就是帧率杀手）" |
| RTOS「任务栈 2048 / 优先级 +2」 | 不可比：本工程 Task_Ui 是 **1536 words(=6 KB) @ prio 26**，且栈余量有实测 | 不适用 |

### 7.2 它的三个"优化技巧"

| 技巧 | 判决与依据 |
|---|---|
| `LV_MEM_CUSTOM` | 不采纳（§7.1 的反证） |

### 7.3 ★ 唯一可采纳的一条：**它的"性能陷阱"警告**

> 「`lv_obj_delete(temp)` —— **使用后立即删除 → 频繁创建/删除导致内存碎片**」

这正是本文 **§4.4 / §6.2 已经实测到的风险**（`frag` 8~27%、`maxblk` 恒 ≈20.2 KB），
而且已经装了 **40% 碎片告警**（§5）。⇒ **采纳形式 = 作为外部佐证记入风险栏，不改代码**。

### 7.4 它提出的真正问题：**"隐藏"比"销毁"快，我们为什么还销毁**

博客方案①（全建 + `LV_OBJ_FLAG_HIDDEN` 显隐，声称切换 **<1 ms**）是对本文策略的**正面对手**。
两边的账（本工程的数字都是实测）：

| | 现状：**用后销毁**（本文） | 博客方案：**全建 + 隐藏** |
|---|---|---|
| 稳态驻留 | **只有当前页**（10~24 对象 ≈ 2.2~4.2 KB） | **三页常驻**（51 对象 ≈ 9.4 KB，永远） |
| 每次切页代价 | 建 **7.7~14.2 ms** + 销 0.9~1.7 ms | ≈0（换标志） |
| 碎片 | `frag` 8~27%（有 40% 告警） | 0（不建不销） |
| 开机占用 | `free 24580 B` | 回到三页全建（`free ≈17324 B`） |

**⇒ 保持现状**，理由两条：① **"用后销毁"是需求方点名要的策略**（需求 2 原文）；
② 隐藏方案的"<1 ms"**来自文章那张表**（同表里还有 `∞ FPS / 0 KB / 0% CPU` 这种不可自洽的
数字，且全文没给测试平台与测量方法）⇒ **不可作为决策依据**，要采纳得先在**本工程测试台上实测**。
（若日后想试：把 `page_destroy()` 的销毁动作换成 `lv_obj_add_flag(tile, HIDDEN)` 即可，
改动是一个函数；判据用 `[UI] 1s` 的分段最大值 + `heap free`，两边都可复现。）

### 7.5 它的数字为何一个都不能用

全文没有一处给出测量方法、工具、测试条件或复现步骤；且表格里出现 `LV_SCR_LOAD_ANIM_NONE`
帧率写成 **∞**、内存 **0 KB**、CPU **0%** —— 这一行本身就不自洽（"无动画"也不是优化手段）。
⇒ 登记为「**不可复现，不采用**」，不进本文任何结论。
