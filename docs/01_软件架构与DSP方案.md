## 1. 定稿参数（一句话版）

| 项 | 定稿值 | 依据 |
|---|---|---|
| 采样率 fs | **2.0 MHz**（TIM 144MHz ÷ 72，TIM8 触发 ADC1） | Δf=488.28Hz ≤ 500Hz ✓；折叠带起点 1.5MHz 全表最优（复算②） |
| FFT 点数 N | **4096**（BH4 窗） | N=8192 收益为零（Δf 已达标），省 32KB+拆包 |
| 读数口径 | **抛物线粗频率 → ±Δf/8 三点 \|X\| → 单点 DFT** | 栅格直读在 δ=0.5 偏 −1.35dB ≈ −12mV@125mV，击穿判据 |
| 抗混叠 | **8 阶巴特沃斯 fc=800kHz**（模拟，前端） | 通带起伏 0.03mV；@1.5MHz −43.7dB → 混叠残留 0.65mV；Qmax=2.56 |

| 标定 | **17 点对数频表（10k~500k），幅值+相位，Flash 持久化** | 消全部 LTI 误差（增益/分压/通带/孔径/相移），残差 0.023mV |

| Urms 口径 | **√(ΣA_k²/2)（交流、频域）** | 频域口径天然排除 u_J，数学上即真有效值 |
| 显示 | 3.5″ 320×480 ST7796S · FSMC 8080 · LVGL（既有） | 用户已拍板，不追 ≥6″ 条款 |

## 4. 采样链定稿（每项都有复算数字）

- **时钟**：SYSCLK 144MHz（既有 board_config）→ APB2 定时器 144MHz；TIM8 ARR=71
  → 触发 fs=2.0MHz。ADCCLK=PCLK2/2=36MHz（上限），转换节拍 15 ADCCLK=0.417µs <
  0.5µs 触发周期，占空 83%。
- **采样时间 SMP=3 ADCCLK**（83ns）：孔径损失 @500kHz 仅 0.29mV/100mV 分量且可被
  标定吸收；SMP=6 会到 1.0mV 且随源阻抗漂移不可精确补偿 —— **宁可短采样**。
  源阻抗要求 Rsrc ≤ 1.1kΩ，运放输出 <100Ω 满足。
- **DMA**：单缓冲（4096 半字 = 8KB，SRAM1 —— **CCM 不能 DMA**）+ **循环模式**，
  门控采集（停 TIM8 断触发源来收帧，而不是停 DMA 循环）。测量非连续流，无需
  环形双 buffer 交替运算。（2026-09-28 落地：DMA 流由 **CubeMX 生成**——
  Circular/半字/High 优先级；模拟输入定在 **PA1（ADC1_IN1）**，避开 PA0 上的
  SW2 按键电路；触发 = TIM8_TRGO 上升沿、DMA 连续请求使能，全部 GUI 配置，
  见 board_config ADC 节与 bsp_adc.c。）
- **为什么不用相干采样**：TIM 整数分频 + 任意 f1 不可同时整周期（复算已证，10.5k/
  42k 无解）→ 单点 DFT 精化读数是必需而非保守，不依赖相干性。
- **为什么 fs=2.0 而不是 1.5**：1.5MHz 的折叠带起点 = fs−500k = 1.0MHz，恰在题面
  u_J≥1MHz 允许域内（残留 16.5mV 击穿判据）；2.0MHz 折叠带起点 1.5MHz，把 u_J 的
  合法域压到只剩"1.5MHz 恰折叠"一点（0.65mV）。六列对比见复算②。

## 5. DSP 算法链与口径规范（op_dsp / op_peak / op_meas）

处理链（全部 f32，4096 点，~15ms）：

```
uint16[4096] → f32（去DC：减均值）
  → ×BH4窗（const 表 16KB in Flash）
  → arm_cfft_f32(4096)               // interleaved re/im（定长 const 实例，见 §5 末）
  → mag[k], k=1..2047                // mag[0] 脏(DC+Nyquist)，丢弃
  → 峰检测：k∈[19,1028]，局部极大，栅格预筛 2·mag[k]/(N·CG) ≥ 2.5mV
  → 每峰：log 域抛物线(限幅|d|≤0.5) → f_c±Δf/8 三点|X|抛物线(限幅) → f_c
  → 单点 DFT @ f_c：A_k = 2|X|/(N·CG)，φ_k = ∠X
  → 标定插值：A/=G(f)，φ−=P(f)
  → 基频 f1 = 最低峰频率；级次 m_k = round(f_k/f1)
  → Urms = √(ΣA_k²/2)；Upp = max−min of **Σ A_k·sin(2π m_k f1 t)**（相位取 0，见口径 2）
```

**口径四条（写死在 op_meas，任何页面只读这里）**：

1. 幅值 = 精化频率上的**单点 DFT**，不是 FFT 栅格值（δ=0.5 栅格直读偏 −12mV@125mV）。
2. Upp = **sin 口径重建**，且**相位一律取 0**（★ 2026-10-16 二次修订）。依据 = 题面
   信号的定义 `u = Σ A_k·sin(2π·f_k·t)`（**各分量零相位**）⇒ 真值形状只由幅值决定。
   **为什么实测相位不能用**（上板查实，`firmware/Operation/Src/{op_meas,op_wave}.c`
   的 2026-10-16 段）：① DFT 的绝对相位参考的是**帧起点**，而帧起点与信号源无关
   （无触发、ADC 自由跑）⇒ 每帧随机；② 标定逐点、**每点各自一帧** ⇒ 相位表每重标
   一次就换一组随机偏移。实测污染：**+19°** → Upp 144.2（真值 134.9）、**~180°**
   → Upp 332.9。⇒ 形状/Upp/波形**只信幅值**（`op_wave.c` 同口径）。禁止 2ΣA、
   禁止 cos 口径（复算④：分别偏 +65mV / +25mV）。
   ⚠️ 代价：对"谐波相对相位非零"的信号会偏 —— 题面不出这种信号；要通用化必须先把
   标定改成"**同帧多分量**"（单音的绝对相位在本装置上不可用）。
3. Urms = √(ΣA_k²/2)（交流口径）。**禁止时域直接算 Σx²/N** —— 第 3 项会把 u_J
   算进去（200mVpp 干扰直通时偏 +140mV 量级），频域口径天然只在分析带内。
4. 频率 = 精化 f_c，直接输出 Hz，不做谐波关系重排（级次 m_k 仅用于 Upp 重建）。

**防御四条（仿真里已踩过坑，MCU 实现必须带）**：
① 栅格预筛（量化噪声地板伪峰的粗频率会乱跳到强峰斜坡上"借"能量过门限，
   33mV 伪峰实测）② log 前加地板 1e−9·max ③ 抛物线 |d|≤0.5 超限弃峰
④ 精化后终判 gate∈[2.5mV, ∞) 且 f_c∈[9k,502k]。
门限 **2.5mV** 的取值依据（★ 2026-10-16：1.5 → 2.5，口径从"单侧"改成**两侧夹逼**）：
- **下界**（把假线挡在峰表外）＝ 最坏混叠残留 0.65mV（防假谱线）· 噪声底 0.053mVrms ·
  **1MHz 干扰的三阶互调产物 ≈1.7mV**（1000−375−125 = 500kHz。旧门限 1.5mV 卡不住它
  ⇒ 它逐帧时进时出 ⇒ 那根谱柱闪烁、Upp 跟着跳 0.9~1.9mV）；
- **上界**（不误伤真分量）＝ 最小真分量 **3.575mVpk**（`tools/sim/s8_e2e_fw.py` 的
  "场景 2：u_b 最小信号 50mVpp"档）⇒ 2.5 留 1.43× 余量。漏检它对 Upp 的贡献可达
  2×3.575 ≈ 7mV —— 会击穿 5mV 判据。

⚠️ 这道门限的职责只是**防假线**：不许改成"把已检出的分量留住"的迟滞 —— 那会让假线
稳定亮着（把假象固化成永久结果）。
门限值有**同值拷贝**两份（`firmware/project_config.h` 的 `APP_PEAK_GATE_MV` 与
`firmware/Operation/Src/op_peak.c` 的静态默认）—— 改一处必须同步另一处。
回归保护 = `Test/test_op_meas.c` 的 **G1**（1.7mV 互调必须检不出）/ **G2**
（3.575mV 真分量必须检出）：只测一侧等于没测（门限改成 100mV 也能过 G1）。

### 5.1 CMSIS-DSP 的用法（审计 2026-09-28，数值实测）

**全工程只调用了 CMSIS-DSP 的一个函数族：`arm_cfft_f32`（FFT）。** 其余全部手写 ——
不是偷懒，而是大多**没有 CMSIS 对应物**；但审计发现两处**没把库用足**，其中一处已修。

> **★ 判据：官方库 vs 自己写（2026-09-28 定，适用于纯 AI 开发）**
>
> 第一判据**不是**"成熟度/性能"，而是 —— **这段代码能不能进 AI 的快速反馈回路**
> （PC 单测，秒级）。
>
> · **能编到 host、能被单测覆盖** → 用官方库。成熟度、优化、维护都是白拿的。
> · **不能**（预编译 .a 是 ARM 机器码、只能上板跑）→ 用它就等于**在 AI 验证最薄弱
>   的地方埋一块盲区**。要么别用；**要么先给它建目标侧测试**（上电自检 / 金标准向量）。
>
> **本轮实测证据**（DSP 链一共查出 3 个功能缺陷）：
> · **2 个在"唯一调用官方库"的那条路径上**（缓冲 2N、输入交织 —— 见修正③），
>   该路径**零测试覆盖**，PC 全绿照旧错；
> · **1 个在手写代码里**（Upp 重建抽点密度 —— 见 §10 修正），被单测当场抓住。
>
> ⇒ 结论：**不是"官方库不好"，而是"没测到的代码才会错"**。官方库的隐式契约
> （缓冲长度、原地与否、输出打包格式、初始化顺序）**编译器查不出来**，AI 最容易
> 在这里写出"看着对"的错码 —— 这正是必须给它配目标侧测试的原因。

**能不能干脆取消 DSP 库勾选（完全不用官方库）？—— 不能，且不划算（有数字）**

- 我们**在用**它：`arm_cfft_f32` + `arm_cfft_sR_f32_len4096`（全工程唯一的官方调用点）。
  `.ioc` 里对应 `X-CUBE-ALGOBUILD.1.5.0.DSPOoLibraryJjLibrary_Checked=true`。
- 取消后没人提供 FFT，必须自己写。代价（按 **8.4 M 复数乘加/帧** 估）：
  - **朴素 DFT**（就是 host 替身那套）：M4F@144MHz 约 **0.47 ~ 2.3 s/帧** ——
    占掉 2 s 判据的 23% ~ 100%+，DSP 全链预算从 ~15 ms 掉到**秒级**。**不可接受**。
  - **手写 radix-4 快速 FFT**：算得过来（~0.5 ms），但**省不掉那 32 KB 旋转因子表** ——
    要么存 Flash（就是现在占的 40.4 KB），要么开机算进 RAM（32 KB，没地方）。
- ⇒ **取消勾选一无所获**：要么慢 30 倍，要么把刚省下的表再加回来。
- 附注：CubeMX 生成的那行 `MX_LINK_LIBS = :libarm_cortexM4lf_math.a` **本来就不管用**
  （`.a` 排在各层之前，单遍扫描时还没有未定义符号 ⇒ 一个成员都不拉，见顶层
  `CMakeLists.txt` §CMSIS-DSP）。真正生效的是工程自己注册的 `cmsis_dsp` imported target。

**★ 让工程"方便 AI 开发"的四条做法（2026-09-28 定，本轮实践验证）**

| # | 做法 | 为什么 |
|---|---|---|
| 1 | **把 MCU 独有的步骤尽量搬进 `Operation/`** | 那层在 PC 上可编可测；留在 `Task/`·`Device/` 的每一步都是盲区。本轮把"FFT 输入装配"从内联搬成 `op_dsp_pack_real_to_cfft()`，缺陷立刻被单测抓住（**S15**） |
| 2 | **契约用编译期断言钉住** | 缓冲长度这类契约编译器查得出：`_Static_assert(sizeof(s_fft) == 2*OP_DSP_N)` 比"上板写穿内存"便宜一万倍 |
| 3 | **搬不走的（库调用本身）配目标侧测试** | `app_engine_selftest()` 上电跑真 `arm_cfft_f32`、校验谱峰位置与幅值 |
| 4 | **改坏一次，确认测试会红** | "测试通过"≠"测试有牙"。本轮把 pack 改回错误写法，S15 当场报 `bad_re=4095`；确认后才恢复 |

> 四条合起来，把"MCU 独有代码"的面积压到最小：现在 DSP 链里**只剩 `arm_cfft_f32`
> 那一行调用本身**没有 PC 覆盖（幅值循环、装配、找峰、精化、口径全在单测里）——
> 而那一行由第 3 条的**上电自检**兜住。

| 环节 | 实现 | CMSIS 里有对应吗 |
|---|---|---|
| 去 DC | 手写（整数累加求均值） | 有（`arm_mean_f32`/`arm_sub_f32`），**未用** —— 整数累加无舍入，更准 |
| 加窗 | 手写乘法 + 生成表 `op_dsp_winh4.c`（518 行常量） | `arm_mult_f32`，**未用**（单层循环，编译器已可向量化） |
| **FFT** | **`arm_cfft_f32`（唯一调用点）** | — |
| 求幅值 | 手写 `sqrtf(re²+im²)` 循环 | 有（`arm_cmplx_mag_f32`），**未用** |
| 找峰 / 抛物线精化 / 单点 DFT / 标定插值 / Upp 重建 | 手写 | **无对应**（本工程特有口径，必须自己写） |

**为什么"有对应函数也不换"（真正的理由，2026-09-28 补充）**

| 函数 | 换掉的代价 |
|---|---|
| `arm_mean_f32` + `arm_sub_f32` + `arm_mult_f32` | 现在的"去 DC → 折 mV → 加窗"是**融合的单遍循环**（读一遍 raw、写一遍 xw/fft）。拆成 CMSIS 调用要 **3~4 遍**内存往返 + 一个中间缓冲 ⇒ **更慢**。且均值用整数累加是**无舍入**的（码值本就是整数），换 float 反而引入舍入。 |
| `arm_cmplx_mag_f32` | 可用，但收益在个位数百分比（2047 个 bin 的 `re²+im²→sqrt`，GCC -O2 在 M4F 上已生成 VFMA+VSQRT）。**这条是唯一"换了不亏"的**，留作可选。 |
| `arm_rfft_fast_f32` | 不只是改调用：它要**自己的 `realCoef` 表**（可能反而多占 Flash），输出是 rfft 的打包序（取谱代码要重写），host 替身也得跟着改。收益 ~6ms，对 2s 判据（余量 130×）无感 ⇒ **不值**。 |
| `arm_sin_f32`（Upp 重建用） | 查表+插值的**近似** sin；本工程 Upp 要 mV 级（对 100mV 分量约 1e-5 相对精度）。换之前得先量化它的误差 —— **没证据不换**。 |

> ⚠️ 上一版这里把理由写成"为了 PC 单测"——**那是错的，已更正**。手写的真实理由是
> 上表两条：**要么 CMSIS 根本没有，要么融合单遍循环更快**。PC 单测是"为什么分层"
> （§1），不是"为什么手写 DSP"。

**修正 ③：MCU 侧 FFT 路径有**两处真缺陷**（2026-09-28 发现并修，最严重的一条）**

起因是审"官方函数到底用了多少"，顺着 `arm_cfft_f32` 的官方约定往下查，发现
**MCU 路径（唯一调用官方库的地方）有两处错，而 PC 单测全绿也照旧错**：

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| ① | **FFT 缓冲只给了 N（4096 floats），官方要求 2N（8192）** | `arm_cfft_f32` 官方文档："buffer of size **2\*fftLen**"；`arm_radix8_butterfly_f32` 索引到 `pSrc[2*(fftLen-1)+1]`=8191 | FFT 写穿 16KB。当时 ELF 里紧邻的正是 `s_xw` ⇒ **每次测量都把 op_peak 要用的加窗时域数据写坏** |
| ② | **输入装配错**：`fft_buf[i] = xw[i]` 把样本**连续**放进去 | CFFT 的 p1 是**交织复数**：`p[2i]`=实部、`p[2i+1]`=虚部。连续放 = 偶数样本当实部、奇数样本当虚部 | 算的根本不是实序列谱，是另一条式子 |

**为什么 PC 单测抓不到**：host 走 `host_dft` 朴素 DFT 替身 —— 它自己处理实序列、
自己写交织输出，**完全不经过 `arm_cfft_f32` 与那两个缓冲**。这正是"替身掩盖 MCU 缺陷"
的教科书案例。

**修法**：`fft_buf` 改 **2N**（32KB，独占 CCM 低半）；`s_xw`（N，16KB）挪到 SRAM1；
输入改**逐点交织 + 虚部清零**。RAM 83568 → 99952 B，sizecheck 的 RAM 预算
96 → 104 KB（**正确性开销**，理由已登记在 `Tools/stm32_size.py`）。

**兜底**：`app_engine_selftest()`（上电跑真 `arm_cfft_f32` 并校验谱峰位置/幅值）——
这条自检正是为这类缺陷加的，两条缺陷它都能抓到。

> ⚠️ **教训**：这条缺陷说明"**官方库用得越少、替身覆盖越多，MCU 侧的黑区就越大**"。
> 反过来说：要用更多官方函数，就**必须先把 MCU 路径的测试补上**（上电自检 / 目标侧
> 金标准向量），否则每多用一个官方函数就多一片看不见的区域。

**修正 ①：实序列没用 real FFT（有收益，但**故意不改**）**
CMSIS 提供 `arm_rfft_fast_f32`（实序列 FFT），对实输入比复数 CFFT 快约一倍。
本工程**故意用复数 CFFT**（理由见 `op_dsp.h` 的"FFT 的选择"）：签名是单缓冲、天生
in-place，省掉 rfft_fast 的双缓冲语义；代价是计算量翻倍（~6ms），对 2s 判据
（余量 130×）无感。⇒ 保持现状。
⚠️ **本文 §3/§5 早期版本写的是 `arm_rfft_fast_f32`，与代码不符，已更正。**

**修正 ②：FFT 表白带了 45KB（**已修**）**
原代码调通用 `arm_cfft_init_f32(&S, 4096)`。它是个 `switch(fftLen)`，为支持 9 种尺寸而
`U` 引用了**全部 9 个** `arm_cfft_sR_f32_len*` ⇒ 链接器把 16~2048 点的 twiddle/bitrev
表**全拉进固件**。实测（`arm-none-eabi-nm` 汇总 ELF）：

| | 修前 | 修后 |
|---|---|---|
| ELF 里 CMSIS FFT 表合计 | **85.3 KB**（twiddleCoef_16…4096 + BitRevTable16…4096） | **40.4 KB**（只剩 `twiddleCoef_4096` 32KB + `armBitRevIndexTable4096` 8.1KB） |
| 固件 FLASH 总量 | 531388 B | **484764 B（−45.5 KB）** |

修法：直接用**定长 const 实例** `arm_cfft_sR_f32_len4096`（在 `arm_const_structs.o` 里；
本工程未 vendor 其头文件，故在 `op_dsp.c` 显式 `extern` 声明 —— 符号名由 `nm` 证实，
不靠猜），调用 `arm_cfft_f32(&arm_cfft_sR_f32_len4096, fft_buf, 0, 1)`。
**等价性由反汇编证实**：`arm_cfft_init_f32` 对 4096 就是把这个 const 结构体的 4 个字段
逐字拷过去（`ldr/ldrd/strh` 三条指令），无其它副作用；顺带省掉每帧一次 init 调用。
`op_dsp.c` 加了 `_Static_assert(OP_DSP_N == 4096)` 兜住"改 N 忘换实例"。

> ⚠️ **PC 测不到这条路径**：host 单测走朴素 DFT 替身，不覆盖 MCU 的 `arm_cfft_f32`。
> 两道兜底：
> ① **结构自检**（离线，已做）= ELF 里**只剩** 4096 的表、且 `arm_cfft_sR_f32_len4096` 在场；
> ② **上电自检**（已加，`app_engine_selftest()`）= 在 MCU 上合成"100mV 单音落在第 100 个 bin"
>    → 跑完整 DSP 链 → 校验谱峰**频率与幅值**。判据本身在 PC 侧由单测 **S14** 钉住。
> 这两条合起来才把这个缺口真正堵上 —— 光看"编译过"或"PC 测试绿"是看不出来的。

## 6. 单频干扰抑制（第 3 项）—— 三层，缺一层就翻车

| 层 | 机制 | 复算数字 |
|---|---|---|
| ① 模拟 | 8阶BW fc=800k：u_J≥1.5MHz 折叠进带前先被压 | @1.5MHz −43.7dB → 残留 0.655mV；@1.0MHz −15.6dB（3.2mV）但镜像 ≥0.5MHz 在带外 |
| ② 频选 | fs=2.0MHz 下 u_J∈[1.0,1.5)MHz 的镜像全落 [0.5,1.0)MHz 分析带外；u_J=1.0MHz 整落在 Nyquist bin，随 mag[0] 丢弃 | S5~S12 全部场景无假峰、无污染 |
| ③ 口径 | 峰检测只扫 [9k,502k]；Urms/波形用峰表重建 | 直通干扰对结果零贡献 |

最坏点 S9（u_J=1.5MHz 恰折叠 + 信号真有 500kHz 分量）：谱线误差 0.549mV、
Upp −0.782mV —— 仍 <5mV。u_J 二次折叠（2.5MHz→0.5MHz）残留 0.002mV，忽略。

**2026-09-28 实测背书**（`Test/test_op_meas.c` 的 S5~S13，`fw.py test` 跑）：

- S5~S8、S10~S12（纯干扰、镜像落点无真分量）：检出峰数 = 真分量数 —— **镜像没有
  变成任何伪谱线**；|ΔUpp| ≤ 0.016mV、|ΔUrms| ≤ 0.004mV。
- S9（镜像恰落在真 500k 分量上，最坏）：500k 读数偏 **−0.652mV** —— 与本节
  0.655mV **逐位吻合**。这是该数字第一次由**器件侧代码**（而非 Python 模型）实测确认。

> **⚠️ 单位口径澄清（2026-09-28，重要）**
> 本节的 **0.655mV 是"输入端折算"**（= LC 输出端，增益已除），与峰门限 1.5mV、
> 判据 5mV **同域**，可直接比。
> `tools/hardware/verify_afe_v2_report.md` §3 的 **1.309mV 是"ADC 端折算"**
> （100mVpk × 0.5端接 × |H| × 4增益）。两者之比 = 2 = 4(增益) × 0.5(端接)。
> ⇒ 该报告 §4 用 1.309mV 去"修正"本节的 0.655mV、并把余量从 7.5× 压到 3.8×，
> 是**跨参考点比较**，结论不成立。预算表与门限都在输入端域，应用 0.655mV
> （且它**保守**：未计端接分压；计入则为 0.327mV，余量更宽）。
> 端接 ×0.5 的真实作用是**降低实际残留**，不是"必须补进预算"。详见 `docs/02` §11。

界面 = **3 页横排滑动**（`lv_tileview`，无页签 / 箭头 / 圆点 / 页码），开机先给一张

每个数跟着它所属的那一页走。

| 页 | 内容 | 数据源 |
|---|---|---|
| 0 时域 | 1 或 3 个完整周期的重建波形（双层 `lv_line`：4px 强调色 30% 晕 + 2px 实线，两层**共用一份点数组**；**用峰表重建绘制**，整数周期对齐、无噪声、有干扰时天然干净）+ 底部三连卡 F1 / Vpp / Vrms（**贴到屏幕底边**，数都在底下 ⇒ 波形吃满整宽） | `op_wave`：按 f1/相位从峰表合成，抽取到 `APP_UI_WAVE_POINTS` 像素列；三个数来自 MeasResult |

键控（2026-10-13 三轮修订：外置物理键、**页签列、场景徽标都已删除**，交互全走触摸屏）：
**左右滑动切页**（切页即刻触发 engine 重测一次）、**周期单键**（页 0 页眉右端只有一个键，
键面写着当前值 `1T` / `3T`，按下描边亮成强调色）、**`CALIBRATE` 按钮**（页 2，点一下
就进标定覆盖层 —— 四轮从"长按防误触"改回"点击"，因为"按了没动静"会被当成坏了）、
**开机页按钮**（`TAP TO START`，整屏也可点）。
上屏数值**统一 1 位小数**（频率 1 位 = 100Hz 分辨率，判据 ≤1kHz）；`THD` 与 `Period`
**不上屏**（题面不要求；THD 仍留在 MeasResult 里，删字段要动尺寸红线断言与 PC 用例）。
**抗"重测 / 重绘风暴"三件套**（2026-10-13 四轮，源自一次上板现场：fps 27 / CPU 73% /
触摸不通）：
① 切页**只在活动页真的变了**时才 `app_engine_remeasure()` —— tileview 在拖动/抖动中会
反复发 `LV_EVENT_VALUE_CHANGED`，每次重测 = 唤醒 engine 跑一整帧（ADC 2ms + DSP ~15ms）；
② `app_ui_poll()` 的业务刷新加 **100ms 闸**（数据再快也只按 10Hz 刷；**翻页不受闸限制**）——
没有它，engine 一旦连续重测，波形就会每拍重建（448×180 面积）⇒ FSMC 写满、UI 任务
挤不出时间读触摸；
③ 触摸侧 **3s 卡死保护**（`app_lvgl.c`）—— 一次按下超过 3s 就强制抬起并压制到读到
真正的抬起：面板/触摸 IC 卡住时会**一直报按下**，LVGL 于是把指针当"按住不放"持续拖
tileview（每帧全屏重绘 + 新点击进不来）。
三件事都带日志：`[TOUCH] 按下 / 抬起 / 读失败`，以及每秒一行
`[UI] 1s: 刷新 N 次 · 页 P · seq S · 堆 free F B`（`UI_STAT_LOG` 可关）。

④ **触摸总线侧**（`bsp_touch.c`，同一现场的第二半）：**I2C 超时 100ms → 5ms** +
失败**重试一次** + 失败**退避 100ms** + 判"数据有效"（`TD_STATUS` 低 4 位必须 ≤5、
坐标 (0,0) 视为垃圾）。理由（RTT 实测）：该读跑在 LVGL 的 indev 回调里，板上读失败率
≈45%（5s 内 140 次）⇒ 100ms 超时意味着**每秒把 UI 任务按在 HAL 里 2.8 秒**，现象就是
"屏像冻住、触摸没反应、日志断档"；而开机那条 `TD_STATUS=FF`（低 4 位 = 15，非法）
会造出一个 **(0,0) 的假按下**，把 tileview 一直拖着走。

⑤ **运行期总线解锁 + 常建 indev**（`bsp_touch.c` / `app_lvgl.c`，同一现场的后半段）：
连续读失败 4 次 ⇒ 跑一次"9 个时钟 + STOP + 重初始化 I2C2"（**运行期版**，与开机诊断
版分开：运行期不扫地址）；`app_lvgl_init()` **无论如何都建 indev**，`bsp_touch_read()`
在未就绪时**每秒重试一次初始化** —— 台面上插好线/换模块**不必重启**就能把触摸捡回来
（旧写法"探测失败就不建 indev"会让触摸死到下次重启）。⚠️ 若诊断显示 **SCL 被外部钉在
低电平**，9 脉冲救不了（主机没法在别人压着 SCL 时发时钟），那属于物理层。

⑥ **降速 100k + 开机寄存器快照**（`bsp_touch.c`）：I2C2 由 400k 降到 **100k**
（边沿触发，时序余量 ×4；只改 BSP 参数，不动 `.ioc`）；开机**只读**扫 `0x00..0x0F` /
`0xA0..0xAF` 各打一行 —— **判据**：整片全 `FF` = 从机没驱动 SDA（物理层）；有结构 =
从机活着、病在内容/模式。（硬件数字滤波在这颗芯片上**不存在**：`stm32f407xx.h` 的
`I2C_TypeDef` 到 `TRISE` 就结束，没有 `FLTR`/`DNF`。）
⚠️ **2026-10-13 五轮更正**：曾据"`01..0F` 全 FF"下过"触摸前端/面板故障"的结论 ——
**那是错的**。按压实测：`按下 (147,186)` 等真坐标报得出来 ⇒ **未触摸时本屏 TD_STATUS
就是 FF（常态）**；真凶是 app_lvgl 的"单次按下超过 1.2s 判卡死"**把真实长按掐了**
（用户现象"触摸几秒后失效"），判据已改成「按着却连续 3s 读不到有效点」。

⑦ **读失败宽限窗 + 两拍确认 + 1.2s 自愈**（`app_lvgl.c`，同一现场的后半段）：
**读失败 ≠ 松手**。LVGL 只认**连续的按下序列**才认拖动 —— 原来"读失败一律报抬起"会把
正在进行的滑动打断、tileview 弹回原位，现象正是**"屏上怎么滑都不换页"**（而点击因为
按/放落在同一点，照样能成）。现在：读失败 200ms 内沿用上一次的状态与坐标（拖动不断），
超窗才判抬起；**单拍按下不上报**（必须连续两拍确认，滤掉总线垃圾蹦出的孤立假按下）；
假按住超过 **1.2s** 强制抬起并压制到读到真正的抬起 —— 假手指造成的"拖屏 + 吃点击"
（屏上表现为帧率从正常的 ≈40 跳进 ≈90、之后触摸像失效）能在一秒出头自愈。
另加每秒一行 `[TOUCH] 1s: 采样 N · 失败 M · 状态 … · 坐标 (a,b)`，让"有没有假手指"
直接可见。

⑧ **时域波形渲染：88% → 22.5% CPU（2026-10-14 七轮，T0–T3）**（`app_ui.c` / `app_engine.c`）：
整页渲染时间的 **93%** 曾花在波形上（T0 消融实测），而根因不是"画得慢"、是**每次都把一大块
面积重填一遍** —— `lv_line` 的对象面积 = 点数组的**最大坐标**（SIZE_CONTENT 口径，取 max
而不是"跨度"）：点从 (16,80) 铺到 (464,212)，对象被撑成 **465×150 ≈ 70 kpx**，而 LVGL 的局部
刷新按**脏区矩形**决策。修法四处：① 显式给对象设 pos/size、把点数组**平移贴紧**到对象原点
（`wave_apply()`，"轨迹扫过的那条带"）② 删 4px"发光层"+ 关圆头（每段省两个圆头填充任务）
+ 点数 320→160（噪声带 80）③ 引擎侧把轨迹抽取从"每 25 点取 1 点"（**混叠抽取**：既画出屏幕
表达不了的毛球、又把垂直行程 Σ|Δy| 放大 ~5×，而 LVGL 画斜线的成本 ∝ Σ|Δy|）改成**格内平均**
④ 构建档 `-Og → -O2`（**只值 1.2×** ⇒ 反证瓶颈在面积×算法，不在指令效率）。
实测：`分段 LVGL` **187 → 26~30 ms/轮**、`handler` **88% → 22.5%**、屏幕最大间隔 **197 → 34~40 ms**、
波形帧率 **5 → 10 Hz**（`APP_MEAS_PERIOD_MS` 200→100；DSP 40% + UI ~25% = 65% ✓）。
**不做**的（都有实测依据）：热函数进 CCM（CCM 已满）、玻璃卡去 α（三卡只占 2%）、
自绘/每列矩形（LVGL 9.5 只能加 draw task，"每列一个矩形"= 449 任务 ⇒ 池爆）、
DMA 搬 FSMC（flush 只占 ~4%，且要保住采样窗静默）、`LV_DRAW_SW_COMPLEX=0`（会砍掉全界面圆角，
属设计取舍）。完整记录见 `_work/lvgl_perf_20261014/帧率与波形流畅度-优化方案.md`。

⑨ **八轮（2026-10-14）：正确性三修 + 一次"能删就删"的评审 + 数据率提速**。三项都落地
（代码已编译/门禁全绿；**上板复核因探针离线延期**，判据见 `_work/chain_review_20261014/`）：
- **正确性**：① 写屏侧的 LCD 总线闸改成"take 成功才 give"（原来无条件 give，会在闸被
  engine 持有时**真的把锁放掉** ⇒ 采样窗静默失效）② 新增 `s_measuring`：engine 从入口到
  发布全程立旗，标定（UI 任务，优先级更高）先等它落 0 再置 `s_buf_busy`（原来只护入口，
  两者会同时读写同一批静态缓冲）③ `lvgl_log_cb` 的级别映射原来把 **ERROR/USER 降成 DEBUG**
  再被 INFO 阈值丢掉 ⇒ `LV_ASSERT_MALLOC` 失败一个字不打；现按级映射。
- **瘦身（ponytail 口径，净减 ~350 行）**：删三套 bring-up 脚手架（`APP_LVGL_USE_DEMO` /
  `APP_LCD_SOLID_TEST` / T0 消融开关）、`bsp_lcd` 整套写吞吐基准（假说已被自己证伪）、
  触摸"写 DEVICE_MODE 唤醒/保活"（实测无效）与开机 32 次寄存器快照、`bsp_adc` 的第二套
  "帧完成"标志 `s_done`、孤儿宏 `BOARD_DSP_CCM_SIZE_KB`、过期内存账口径、`card_value_create`
  单调用点包装；DWT 计时从 `bsp_lcd` 搬到 `bsp_tick`（那是通用时基）。
- **显示侧删白付**：频谱柱改**直写高度**（原来 300ms 动画被 100ms 数据反复打断 ⇒ 柱区
  ≈0.86 Mpx/s 持续重绘）；波形加**变化检测**（所有列 ≤1px 就不设点、不脏区）；标定覆盖层
  盖着时停刷页 2；关掉空 HT 中断（976 次/s）；堆读数降到 5s 粒度。
- **数据率**：引擎节拍改"**睡到下一个绝对时刻**"（旧写法把链长约 40ms 叠加进周期 ⇒ 实测
  只有 ~7Hz）；新增 `[ENG] 一拍 …（采集 + DSP + 发布）` 分段计时；**DSP 三处 double→float**
  （`op_meas` 的 Upp 重建 1536 次 `sin`、`op_wave` 的 `sin`、`op_peak` 的 384 次 `cos/sin`
  锚点；`raw_publish` 的方差走 float+Kahan）—— 本工程只有单精度 FPU，double 全是软浮点，
  这一项预估把链长从 ~40ms 压到 ~20ms。**注意**：精度由 Operation 的 PC 单测（`fw.py test`）
  与板上 `app_engine_selftest` 双向兜底，两处都必须绿才算数。

**LVGL 的 lv_timer_handler 必须周期性被调**（ui 任务自循环），这是既有骨架的形态。

u_a/u_b/u_c 模式不做成三套代码：算法与界面唯一（屏上**不显示**当前场景 ——
三个场景在屏上判不出，说明见 `Task/Inc/app_ui.h` 文件头）。

## 8. 任务结构与时序预算

**实现定稿（2026-09-28）**：两任务 + CubeMX 的 defaultTask。

| 任务 | 优先级 | 栈(words) | 职责 | 阻塞点 |
|---|---|---|---|---|
| Task_Engine | 22 | 1024 | 启动 ADC→**阻塞等帧信号量**→DSP 链→发结果 mailbox；标定建表 | 二值信号量（DMA 完成，ISR 给）|
| Task_Ui | 23 | 1536 | `lv_timer_handler` 循环 + 页面状态机 + 触摸 + 标定交互 | 自主周期 10ms |
| defaultTask（CubeMX） | 24 | 256 | 心跳 / 闪灯 / RTC 复查（`app_rtos_run`） | `osDelay(10)` |

时序（2s 判据）：DMA 采样 2.048ms → FFT ~3ms → 精化 3 分量×4 点×4096 ~5ms →
重建/渲染 <10ms → **单页刷新 <25ms**。连按 80 次键都能在 2s 内完成。

> ★ **2026-10-14 八轮：上表是"设计值"，实测值以两个探针为准**（探针本身也在这一轮补齐）：
> · **链长**：`[ENG] 一拍 X ms（采集 a + DSP b + 发布 c）`，每 5s 一行（`app_engine.c`）。
> · **节拍**：`APP_MEAS_PERIOD_MS` 现在是 **100ms**，且引擎改成"**睡到绝对时刻**"
>   ⇒ 实际数据率 ≈ 10 Hz（不再被链长叠加：旧写法 100 + 链长 ≈ 140ms ⇒ 只有 ~7Hz）。
> · **渲染/写屏**：`[UI] 1s`（刷新次数/最大间隔/分段 等待·业务·LVGL）与 `[LVGL] diag`
>   （窗口 ms + flush px + px/s + handler µs + DWT 的 flush 时长）。
> · **内存预算唯一口径**：`Tools/stm32_size.py` 的 `BUDGETS`（RAM 120KB / FLASH 640KB）。
>   别在别处再写一套数字（本仓曾出现 104/112/120 与 "21.4KB/27.5KB 界面开销" 三套并存）。
> · 波形渲染的大头已在 §7 ⑧ 说明：**对象面积**而不是"画线速度"。

> ★ **"时域页帧率太低"的真相（2026-10-13 六轮）**：不是画不动 —— FSMC 现役时序
> **AS=2/DS=8 ⇒ 76.4 ns/字 ≈ 13 Mpx/s**，一次全屏重绘只要 ≈12ms（理论上 80fps 有余），
> 而且屏上内容**只在"新结果到达"时才变**（波形由峰表重建、数字由结果驱动）⇒
> **屏上帧率 ≡ 测量节拍**。原 `APP_MEAS_PERIOD_MS = 500` ⇒ 2 fps，观感就是"卡"。
> 已改 **200ms（≈5 fps，DSP 占空比 20%）**；数字滚动动画同时收到 140ms（必须短于节拍，
> 否则动画互相打断）。要让波形"真流动"只能让 ADC 连续采集，而那会毁掉**采样窗静默**
> （LCD 噪声灌进 AFE）⇒ 不采用。

内存预算（**2026-10-13 四轮实测**：RAM **105832 B/128 KB = 80.7%**（`fw.py sizecheck` 退 0），
CCM 32 KB/64 KB = 50%）：
`fft_buf` 2N=32KB 独占 CCM 低半 + **LVGL 主堆 32KB 占 CCM 高半**（两半合计把 CCM 用满，
见 `board_config.h` 的 `BOARD_CCM_*`）+ `s_xw` N=16KB 与 DMA 缓冲 8KB 在 SRAM1
+ **LVGL draw buffer 45KB**（480×48×2，2026-10-13 横屏后由 30KB 涨上来）
+ **LVGL 第二块池 4KB @SRAM1**（`BOARD_LVGL_MEM_EXT_KB`：一轮那版 4 页界面要
27.5KB，主池 + 板侧基线约 32~33KB 挤不下 ⇒ 补 4KB 凑 36KB；二轮删掉参数页后
界面回落到 **≈21.4KB**（四轮"一框一根"的谱线框又花回 ≈4.6KB），这 4KB 继续
留着当余量 —— 池耗尽是**静默失败**）
+ 两个任务栈 10KB + FreeRTOS 堆 15KB。
**RAM 门禁上限 104 → 112 → 120 KB**（`Tools/stm32_size.py` 的 `BUDGETS`；2026-10-13
六轮**用户两次当场授权**，原话"为什么你要限定在 104KB 门禁线？可以放开啊"→"放开到
120kb"）—— 当时实测 **106264 B = 103.8 KB = 81.07%**；120 = 93.75%，**余量只剩 8 KB**
⇒ 到这量级别再提上限，该做的是把缓冲挪回 CCM 或砍功能。放宽的用途是给 UI/引擎留增量
（六轮把"原始帧口径"的轨迹与统计接进 UI 后已贴到旧线）；**不是**"当前用量 ×1.1"那种会
随用量漂移的自动放宽。

> ★ **同轮的另一处根因修复：引擎任务优先级 26 → 22（降到 UI 之下）**。原设计写
> "engine 26 > defaultTask 24 > ui 23，测量永远优先于界面" —— 但 DSP 一拍是 **40ms
> 纯计算**，"最优先"等于"每 200ms 硬插 UI 一刀"。现象（用户原话）：**"波形很明显从上
> 到下刷新、整体一卡一卡"** —— 波形区 180px 分 4 条横带渲染，每两条带之间被插 40ms。
> 降级后引擎用 UI 的 10ms 睡眠缝跑（40ms 活摊成 ~55ms 墙钟）。**安全性已核**：帧满时
> ISR 先关 TIM8 触发源 ⇒ 引擎晚 10ms 收尾也不会让循环 DMA 覆盖单缓冲。判据进了日志：
> `[UI] 1s: … 最大间隔 N ms`（贴 UI 节拍 = 10ms 级；被插队则 40+）。
> ⚠️ 30KB→45KB 那条是横屏的连带代价（draw buffer 宽度按逻辑宽 480 算，见
> `project_config.h` 的 `APP_LVGL_DRAW_BUF_LINES`）：改分辨率前先算这笔账。
**结果结构体 ≤84B 过队列**（2026-10-13 UI 重构：峰表 5×(f32,f32)+THD，路线 A 最小改动），波形/谱线渲染数据只在 ui 层
静态区生成 —— 不许把 4KB 级数组塞结果体（历史教训：MeasResult 4144B 局部变量爆栈）。

> **⚠️ 2026-09-28 实现定稿（本节任务的落法，历经两次修订）**
>
> **第一次修订**曾把 engine 降级为"10ms 轮询态机"（IDLE→ACQ→PROC，免队列/免信号量）。
> **第二次修订（当前）改回真任务**，理由是轮询版有三处硬伤：
> ① 采集完成靠 10ms 轮询 —— 最多白等一拍（~10ms）且抖动；② 重测请求要等下一拍；
> ③ 结果单例的"无锁"仅靠"engine/ui 同任务"侥幸成立。
>
> **现状**：`Task_Engine`(26) + `Task_Ui`(23) 由 `app_tasks.c` 用 `xTaskCreateStatic`
> 静态创建（栈/TCB 是 static 数组，不动 15KB 的 FreeRTOS 堆）。三条跨任务通路：
> · **帧就绪**：DMA 完成中断 `xSemaphoreGiveFromISR` → engine `bsp_adc_wait_frame()`
>   阻塞取（等待期让出 CPU；ISR 优先级 5 = `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`，合法）；
> · **重测请求**：UI 调 `app_engine_remeasure()` → `xTaskNotifyGive` → engine 的
>   `xTaskNotifyWait` 立刻醒（否则睡满 `APP_MEAS_PERIOD_MS`）；
> · **结果发布**：1 深队列 + `xQueueOverwrite`（mailbox = 跨任务双缓冲），
>   UI 侧 `xQueuePeek` —— `MeasResult_t` 仍 ≤84B，但不再依赖"同任务"。
>
> **新增的 O1 落地**：engine 采集窗内置 `s_acquiring`，UI 任务见它即推迟 FSMC 刷新
> （`app_engine_acquiring()`）—— 机制性消除"采集瞬间 LCD 总线噪声灌进 AFE"。
>
> **采集侧不做乒乓双缓冲**（诚实标注）：门控采集下生产者 2.048ms/帧、消费者 DSP
> ~13ms/帧，快 6 倍 ⇒ 双缓冲只会让新帧盖掉未处理完的旧帧。真正需要它的是
> **双帧变频识别 u_J**（两个 fs 各一帧交叉比对，残留 1.31mV→~0.1mV），属 DSP 级改动，
> **当前未实现**（见 `docs/02_优化方案_硬件与软件.md`）。
>
> **降级**：`app_tasks_init()` 失败时组合根退回"单循环"（`app_engine_poll` 内联），
> 保底可用、不静默变砖。link 任务不建（RTT 日志走 `LOG_*` 直写）。
> DSP 双缓冲落 CCM 低 32KB（section .ccmram，链接脚本 ASSERT 兜底）。

## 9. 硬件侧约束（前端定稿指标，交硬件实现）

- 输入：BNC 座 + 50Ω 对地端接（题面 50Ω 电缆暗示匹配；分压 ×0.5 由标定消）。
- 放大：×4（±225mV 最坏输入 → ±0.9V），RRIO 运放，5V 单电源 + 1.65V 虚地偏置。
- 抗混叠：8 阶巴特沃斯 fc=800k（Q 序列 0.51/0.60/0.90/2.56，无高 Q 节；通带起伏
  0.03mV/100mV；@1.5MHz −43.7dB）。**必须实测验证**：制作后用信号源扫频录入标定
  表时，残差即暴露制作误差。
- 电源：5V 单路入，模拟/数字 LC 分割；ADC 基准用 VREF+ 引脚接低噪 3.0V 或 3.3V。
- **自干扰源管理**：背光**恒亮、禁 PWM**（2026-09-28 拍板）—— PWM 调光的谐波列
  全落 10k~500k 分析带内，是固定频率伪峰制造机（固定频率+等间隔，最像真信号的
  假信号）；竞赛装置不需要调光，PB0 只许 GPIO 数字开关（PB0 恰是 TIM3_CH3
  复用脚，CubeMX 里严禁改配 PWM）。
- 上电自检：ADC 采已知电平（虚地）判通道活性；标定表 CRC 校验，缺失则 UI 提示进标定。

> **⚠️ 2026-09-28 修正：Upp 重建的抽点密度（PC 单测发现并已修）**
>
> `op_meas` 原先**固定 512 点/基波周期**，注释称"与 8192 点差 <0.01mV"。

>
> 已改为按 m_max 自适应（`max(512, 32·m_max)`，上限 4096）：m≤16 时**零额外开销**
> （仍是 512 点），m=50 时 1600 点；实测残差降到 **−0.002mV**。
> 回归保护 = `Test/test_op_meas.c` 的 **S13**（修复前必失败、修复后 |ΔUpp|<0.01mV）。

## 11. 标定流程（op_cal，比赛现场大杀器）

题面明确"允许携带自用信号发生器"+"各参数设置值作为标称值" → 全部 LTI 误差可被
赛前一次标定吃掉（复算：一个通带被削 3dB 的前端，标定后 41.8mV 误差 → 0.52mV）。

- 流程：CAL 长按 → 按提示接信号源 100mV 单音 → 装置在 17 个对数频点
  （10k→500k）各测幅值/相位 → 除以设置真值得 G(f)、P(f) 表 → op_flash 持久化。
- 使用：检出每个分量后按 f 对数插值修正。表点间隔处残差 0.023mV（实测）。
- 标定时无干扰，混叠残留**不在标定表内**——它是预算表里唯一"标定消不掉"的行。

## 13. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 模拟前端制作不达标（衰减/噪声/失真） | 高 | 误差预算 7.5× 余量；标定兜底 LTI 项；上电自检+扫频复测 |
| u_J 恰设 1.5MHz 整 | 低 | 已是预算内最坏点 0.65mV |
| LCD 3.5″ 与题面 ≥6″ 不符 | — | 用户已拍板接受（不追该条款） |
| CCM/DMA 落区错误 | 中 | DMA 缓冲强制 SRAM1（engine 的 s_adc_buf；链接脚本段校验进 sizecheck） |
| LVGL 调度饿死按键 | 中 | **已消解（2026-09-28）**：Task_Ui 独立任务（prio 23）+ 10ms `vTaskDelay` 节拍；engine 虽为最高优先级，但**阻塞在 ADC 帧信号量上**，不长期占 CPU |
| 多任务并发（本轮新引入） | 中 | 三条跨任务通路全走 FreeRTOS 原语（信号量 / 任务通知 / 1 深队列），无裸共享变量；LVGL 只由 Task_Ui 单任务触碰。**待上板**：用 `uxTaskGetStackHighWaterMark` 复核两个任务栈余量（校验函数尚未加回） |
| 采样窗静默不彻底 | 低 | UI 任务**已进入渲染后**才被 engine 抢占的边角，仍会在采集窗内写 FSMC；彻底消除需 FSMC DMA + 双缓冲（后续项） |
| Upp 重建抽点密度不足（大阶次） | 中 → **已消** | 2026-09-28：改为按 m_max 自适应（512→1600@m=50），实测 −1.75mV → −0.002mV；S13 单测钉住（见 §10 修正） |
| **MCU 侧 FFT 路径无 PC 覆盖** | **高 → 已消** | 2026-09-28：正是这个黑区里藏了**两处真缺陷**（FFT 缓冲只给 N 应为 2N；输入未交织+虚部未清零）—— PC 全绿照旧错。已修；兜底 = `app_engine_selftest()` 上电自检（跑真 `arm_cfft_f32`）+ S14 钉住判据（见 §5.1 修正③） |
| 板卡自干扰（背光 PWM 等） | 高→低 | **背光恒亮禁 PWM**（§9）；固定频率伪峰源在源头禁用 |
